# AI 视频生产平台数据字典

- 数据字典性质：统一逻辑数据模型 + 建议字段与约束
- 规则：设计稿确认的既有 schema 是迁移基线；凡标注“待核实/建议新增”的内容，实施前必须检查现有 migrations、models 和 repositories。不得直接用本字典重建数据库或删改旧列。
- SQLite 默认；时间/金额/JSON 列的物理表示需兼容现有代码。本字典使用逻辑类型描述。

## 1. 数据建模总则

1. SQLite 只保存元数据、状态、关系、配置元信息、Job 参数快照与成本；小说/剧本/分镜正文和媒体文件在文件系统，文档历史由 Git 管理。
2. 九个核心业务实体：Project、Episode、Asset、Doc、Shot、Task、Job、Review、Knowledge。
3. 身份实体：AppUser、Role、Permission；关联实体：user_role、role_permission、project_member、project_tag、session。
4. 其他技术实体包括 ProviderConfig、GenerationProfile（建议）、ExtractionRun、ExtractionItem（设计稿修订记录明确有抽取草案）、AssetImage（若现有实现采用单独图片登记表；否则沿用现有资产字段/路径机制）。
5. 各模块唯一写入归属：Project/项目中心；Episode/Doc/Shot/创作中心；Asset/资产中心；Task/Job/成本/生成中心；Review/审核中心；Knowledge/设定中心；AppUser/Role/Permission/ProviderConfig/系统设置。
6. `project_id` 是项目级数据隔离的重要键。全局资产/Knowledge 可以用空 `project_id` 表示，但必须有明确的权限和引用规则；不能仅凭 `NULL` 就允许任何用户修改。
7. 业务主键优先沿用现有 INTEGER ID；不要未经兼容性评估将现有 ID 改成 UUID。
8. 外键与级联策略必须逐表定义；文件系统副作用不由外键自动完成，需通过 Service 维护一致性。

## 2. 数据库实体关系概览

```text
AppUser ──< user_role >── Role ──< role_permission >── Permission
   │
   ├── owns Project (owner_id; ON DELETE RESTRICT)
   └──< project_member >── Project
                               ├──< Episode ──< Shot
                               ├──< Asset ──< AssetImage/files
                               ├──< Doc metadata ── filesystem + Git
                               ├──< Task ──< Job (one task may have retries/multiple jobs)
                               ├──< Review (target_type/target_id and version anchor)
                               └──< Knowledge

ProviderConfig ── supplies provider/model metadata to Job snapshots
GenerationProfile ── provides reusable params to create Job snapshots
Doc ──< ExtractionRun ──< ExtractionItem ── accepted Asset or exported Markdown
Shot ──< Job
Job/Doc/Shot ──< Review
```

关系图为逻辑关系。落库外键以当前真实 schema 及 SQLite 对多态目标的限制为准；`Review.target_type/target_id` 这类多态引用不能声明成一个普通外键，应通过 Service 校验存在性、项目归属和版本。

## 3. 字段类型约定

| 逻辑类型 | 表示与规则 |
|---|---|
| ID | SQLite INTEGER PRIMARY KEY，引用已有 ID 时使用实际列名 |
| TEXT | Unicode 文本；名称/代码应有长度上限；长正文不放入 DB |
| BOOLEAN | SQLite INTEGER，0/1；在 Python API 层映射 bool |
| DATETIME | 遵守现有数据库时间格式。已有字段不强行转换；新增表统一格式应在 CURRENT_SCHEMA 核验后确定。当前设计稿有本地时间语义，不得混算 last_opened_at 和 updated_at |
| JSON TEXT | 序列化 JSON；写入/读取需校验 schema。禁止用 pickle 保存外部可控数据 |
| RELATIVE_PATH | 相对于配置根目录的安全路径；不接受客户端绝对路径；服务端在使用前重新规范化验证 |
| ENUM/Literal | 应用层白名单校验，遵照已有设计不盲目在 SQLite 加 CHECK 约束（新增表是否可用 CHECK 需先评估迁移扩展性） |
| MONEY | 推荐整数最小货币单位或 Decimal 字符串，禁止以二进制浮点作为唯一金额真相源；保留币种和计量单位 |

## 4. 已确认/既有核心表

> 表/列的物理细节需以当前 `migrations/*.sql` 为准。以下主要是逻辑字段与约束；如实际列名有差异，应在代码映射中沿用实际列名并更新此文件，而不是无理由重命名。

### 4.1 `project` — 项目

| 字段 | 类型 | 必填 | 约束/说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键；保留既有 ID |
| `name` | TEXT | 是 | 去除首尾空格，不能为空；删除确认时用于精确匹配 |
| `description` | TEXT | 是 | 设计稿记录默认空串，上限 500 字 |
| `owner_id` | ID/FK | 是 | 所有人；`app_user.id`，删除账号时 `ON DELETE RESTRICT`；创建时取当前登录用户，后续仅通过所有权转移操作修改 |
| `status` | ENUM | 是 | `active`/`archived`；应用层 Literal 验证 |
| `created_at` | DATETIME | 是 | 创建时间；不因查看/归档改变 |
| `updated_at` | DATETIME | 是 | 最后内容修改时间；集/镜头/资产等内容变动时更新；打开项目、归档不能推动它 |
| `last_opened_at` | DATETIME/NULL | 否 | 最近打开时间；NULL 表示从未打开，不能作为内容修改时间 |
| `tags` | 逻辑关联 | 否 | 通过 `project_tag`/当前实现存储，最多 10 个标签、每个最长 20 字、去重；数组读取需有明确顺序或不承诺顺序 |
| `episodes_count` | 派生数值 | — | 不建议作为权威列，列表查询聚合计算 |
| `shots_count` | 派生数值 | — | 同上 |
| `assets_count` | 派生数值 | — | 同上 |
| `done_episodes_count` | 派生数值 | — | 基于 `episode.status='done'` 聚合 |

**索引建议：** `(status, last_opened_at DESC, id DESC)`；`owner_id`；项目列表所用的标签检索通过 `project_tag` 索引。若现有实现的排序表达式不同，保持输出行为相同。

### 4.2 `project_tag` — 项目标签

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `project_id` | ID/FK | 是 | 指向 project；随项目删除 |
| `tag` | TEXT | 是 | 归一化后的标签文本 |

**主键/唯一性：** 建议复合主键 `(project_id, tag)` 或唯一索引，防止同一项目重复标签。追加标签必须合并去重后截断/验证，不能误将批量追加实现成整组替换。全局 tag 读取需有稳定排序，不得依赖无 `ORDER BY` 的 SQLite 扫描顺序。

### 4.3 `project_member` — 项目协作人

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `project_id` | ID/FK | 是 | `project.id`，项目删除时 CASCADE |
| `user_id` | ID/FK | 是 | `app_user.id`，用户删除时 CASCADE |
| `added_by` | ID/FK/NULL | 建议 | 添加者；若现有 schema 已有该列则沿用；不作为通用业务审计系统 |
| `created_at` | DATETIME/可选 | 否 | 添加时间；如果当前没有则不为此单独破坏迁移 |

复合唯一约束 `(project_id, user_id)`；项目所有人本身不必重复存为协作人。只有管理员/所有人有权添加/移除协作人；协作人不能删除项目、管理成员或转移所有权。

### 4.4 `episode` — 集/创作单元

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `project_id` | ID/FK | 是 | 属于项目；项目删除时按现有级联逻辑处理 |
| `number`/现有序号列 | INTEGER | 是 | 集序号；以实际 schema 列名为准，在事务内分配以防并号 |
| `title`/现有名称列 | TEXT | 待核实 | 如果当前模型提供标题则沿用；不假设已有此列 |
| `status` | ENUM/TEXT | 是 | 必须支持 `done` 用于集级定稿计数；其它已有值从当前 Literal/校验中读取 |
| `created_at` | DATETIME | 是 | 创建时间，列名/默认值以迁移为准 |
| `updated_at` | DATETIME | 视 schema | 集自身内容修改的时间；是否实际存在待核实 |

**规则：** 集的创建/删除只属于创作中心；项目中心仅显示集数和已定稿计数。删除集前明确展示将删除/解除关联的镜头数，并按当前删除策略清理。

### 4.5 `asset` — 角色/场景/道具资产

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `project_id` | ID/FK/NULL | 依当前 schema | 项目资产归属某项目；NULL 可代表全局资产池（若当前实现支持）；必须执行全局资产授权 |
| `type` | ENUM | 是 | 角色/场景/道具，逻辑代码建议 `character`/`scene`/`prop`，具体以当前 Literal 为准 |
| `name` | TEXT | 是 | 去首尾空格；同归属范围、同类型内唯一；冲突返回 409 |
| `description` | TEXT | 建议 | 视觉外观、设定描述等；检查当前已有字段避免重复新增 |
| `consistency_prompt` | TEXT | 视 schema | 角色/场景一致性提示词；只在资产中心修改 |
| `knowledge_id` 或关联表 | ID/FK/JSON | 待核实 | 设计稿提到设定文档引用；优先沿用已有引用方式。多条引用时建议独立关联表 |
| `reference_images`/路径关联 | JSON TEXT 或关联表 | 待核实 | 当前图片 API 写入 `data/files/<asset_id>/<uuid>.<ext>`。不要未检查 schema 就新增第二种记录真相 |
| `created_at` | DATETIME | 是 | 创建时间 |
| `updated_at` | DATETIME | 建议 | 内容变更时间；项目 updated_at 应同事务更新 |

**唯一性：** 同一归属范围 + type + name 唯一。SQLite 中 NULL 参与唯一索引需谨慎，若项目级与全局重名策略不同，用应用层检查 + 相应索引/部分索引表达。

### 4.6 `shot` — 分镜镜头

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `episode_id` | ID/FK | 是/现有路径基线 | 当前 API 形态为 `/api/episodes/{id}/shots`；先保持兼容。镜头逻辑归属于某集 |
| `document_id` | ID/NULL | 待定/建议 | 设计稿逻辑上写“Shot 属 Doc（剧本）”，但当前 API 按集管理；只有核查当前 schema 后才决定是否新增该关联 |
| `number`/序号列 | INTEGER | 是 | 集内镜号，在事务中分配 |
| `shot_size`/景别字段 | TEXT | 视 schema | 镜头景别；现有物理列名待核实 |
| `description`/画面内容 | TEXT | 视 schema | 画面描述 |
| `duration_seconds`/时长 | REAL/INTEGER | 建议 | 目标镜头时长；单位必须在 API 明确 |
| `dialogue` | TEXT | 视 schema | 对白/旁白；长文档正文仍保存在文件，不在此复制完整剧本 |
| `camera_movement`/运镜 | TEXT | 视 schema | 运镜信息 |
| `image_prompt` | TEXT | 建议 | 图像提示词 |
| `video_prompt` | TEXT | 建议 | 视频提示词 |
| `asset_ids` | JSON TEXT/既有类型 | 是/如当前字段存在 | 当前设计稿明确提到 `ShotIn.asset_ids`；只储引用 ID，不复制资产正文 |
| `created_at`/`updated_at` | DATETIME | 按 schema | 时间字段；内容改变应更新项目的 `updated_at` |

**规则：** 一条 Shot 可以关联 0..N 个 Job；每个 Job 冻结所用提示词/参数，不随着镜头后续修改而改变。删除资产前须检查被引用镜头。

### 4.7 `app_user` — 账号

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `username` | TEXT | 是 | 唯一、登录用户名；超级用户基线用户名为 `superadmin` |
| `display_name` | TEXT | 是 | 显示名 |
| `password_hash`/既有 hash 列 | TEXT | 是 | scrypt hash；绝不回传前端，口令明文不得落库 |
| `is_superuser` | BOOLEAN | 是 | 与角色授权并行；超管权限由此字段判定 |
| `is_active` | BOOLEAN | 是 | 停用用户不可登录/访问业务 API |
| `must_change_password` | BOOLEAN | 是 | 首次登录要求更新口令 |
| `last_login_at` | DATETIME/NULL | 否 | 最近登录时间 |
| `created_at` | DATETIME | 以 schema 为准 | 创建时间 |

安全不变量：不可通过普通 API 停用/改角色/重置 `superadmin`；不能停用自己或改自己角色；用户列表必须在服务器过滤层级。

### 4.8 `role` — 角色

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `code` | TEXT | 是 | 固定代码 `admin`、`editor`、`viewer`（以当前 seed 为准） |
| `name` | TEXT | 是 | UI 显示名称 |
| `description` | TEXT | 建议 | 角色说明 |

当前 admin 角色权限列在 UI 中禁用编辑，保持现有保护策略。

### 4.9 `permission` — 权限点

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `code` | TEXT | 是 | 当前固定 20 个 code；例如存在 `project:read`、`project:write`、`system:config`、`user:read`、`user:write`、`user:assign` 等。完整列表必须从现有种子/DB读取，本文件不重新定义剩余代码 |
| `name` | TEXT | 是 | 可读名称 |
| `group`/domain | TEXT | 视 schema | 权限矩阵分组 |

### 4.10 `user_role` — 用户角色关联

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `user_id` | ID/FK | 是 | `app_user.id` |
| `role_id` | ID/FK | 是 | `role.id` |

复合唯一/主键 `(user_id, role_id)`。超级用户可以挂全角色用于界面显示，但授权结果直接基于 `is_superuser` 返回全集。

### 4.11 `role_permission` — 角色权限关联

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `role_id` | ID/FK | 是 | `role.id` |
| `permission_id` | ID/FK | 是 | `permission.id` |

复合唯一/主键 `(role_id, permission_id)`。矩阵保存时应在一个事务内更新，admin 角色不可通过 UI 改权限。

### 4.12 `session` — 登录会话

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `user_id` | ID/FK | 是 | `app_user.id`，用户删除时清理会话 |
| `token_hash`/既有令牌字段 | TEXT | 是 | 如果现实现存随机令牌或哈希，应沿用且不回传库内容；具体列名待核实 |
| `expires_at` | DATETIME | 是 | 默认 12 小时，可通过 `FASTVIDEO_SESSION_HOURS` 配置 |
| `created_at` | DATETIME | 是 | 创建时间 |

口令有效期与会话有效期是两个不同概念；当前系统不做口令周期过期。

## 5. 配置与生成数据表

### 5.1 `provider_config` — Provider 双轨配置（既有）

设计稿确认该表配置固定五种能力 × 本地/云端共 10 个槽位；密钥只从环境变量读取，不进入表和响应。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID/既有主键 | 待核实 | 沿用实际 schema |
| `capability` | ENUM/TEXT | 是 | `text`、`image`、`video`、`tts`、`music`（现有代码如采用别名，需映射） |
| `execution_mode` | ENUM/TEXT | 是 | `local`/`cloud`，或当前字段等价名称 |
| `provider_code` | TEXT | 是 | adapter/provider 标识，不含密钥 |
| `model_code` | TEXT | 是 | 模型或档位 ID |
| `is_enabled` | BOOLEAN | 是/建议 | 是否允许选择 |
| `is_default` | BOOLEAN | 是 | 每类能力只有一个有效默认路线；须按当前表约束和业务策略核对 |
| `secret_env_name` | TEXT/派生 | 建议 | 如 `FV_KEY_<PROVIDER>` 的变量名；环境变量值不存库 |
| `config_json` | JSON TEXT/可选 | 建议 | 不含密钥的非敏感 provider 配置 |
| `updated_at` | DATETIME | 视 schema | 最近配置更新时间 |

校验：不能把 API key 放在 `config_json`；每种能力只能有一个有效默认。视频云端档不会仅因 `is_default` 自动提交云端；逐镜头显式同意优先级更高。

### 5.2 `task` — 业务任务（九实体）

> 物理 schema 待核实/建议新增。Task 与 Job 分开：Task 是用户可跟踪的工作项，Job 是一次具体执行。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `project_id` | ID/FK | 是 | 项目归属 |
| `task_type` | ENUM | 是 | `generation`/`review`/`manual`/`extraction`，按实际支持收口 |
| `title` | TEXT | 是 | 用户可读任务标题 |
| `status` | ENUM | 是 | 由相关 Job/Review 状态协调；不得另建任务队列 |
| `assignee_user_id` | ID/FK/NULL | 可选 | 指派用户；必须检查用户层级/项目授权；如果坚持业务表不引用账号，先提出设计冲突，不得悄悄改为无主任务 |
| `target_type` | TEXT | 是 | 关联对象类型，如 `doc`/`shot`/`asset`/`job` |
| `target_id` | ID/TEXT | 是 | 目标主键；多态关联由 Service 校验 |
| `due_at` | DATETIME/NULL | 否 | 人工任务可选截止时间 |
| `created_at` | DATETIME | 是 | 创建时间 |
| `updated_at` | DATETIME | 是 | 状态/标题变更时间 |

### 5.3 `job` — 生成作业与成本真相源（九实体）

> 二期核心表；字段名须兼容当前已有实现，以下为最小逻辑契约。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键；外部显示稳定 Job ID |
| `project_id` | ID/FK | 是 | 项目归属，执行前再做授权检查 |
| `task_id` | ID/FK/NULL | 可选 | 对应业务 Task；直接生成的 Job 可为空/自动生成 Task，需统一策略 |
| `episode_id` | ID/FK/NULL | 否 | 相关集 |
| `shot_id` | ID/FK/NULL | 否 | 相关镜头；多个 Job 可关联同一镜头 |
| `capability` | ENUM | 是 | `text`/`image`/`video`/`tts`/`music` |
| `kind` | ENUM | 是 | 保持 adapter 请求类别：`text`/`image`/`video_local`/`video_cloud`/`tts`/`music`；如扩展 extraction 用 capability + task_type 映射，不任意改旧枚举 |
| `execution_mode` | ENUM | 是 | `local`/`cloud`；用于明确路由，不通过 model name 猜测 |
| `provider_code` | TEXT | 是 | 使用的 provider/adapter 标识 |
| `model_code` | TEXT | 是 | 精确模型/模型档位 ID |
| `adapter_version` | TEXT/NULL | 否 | adapter/脚本版本快照，便于复现 |
| `prompt_snapshot` | TEXT/NULL | 否 | 该 Job 使用的提示词快照；正文大文件可用引用+哈希，不能复制整篇文档 |
| `params_json` | JSON TEXT | 是 | 参数快照；不包含密钥、不允许 shell command 注入字段 |

## 10. 索引与完整性要求

建议（需对照 EXPLAIN QUERY PLAN 与现有索引后再添加）：

- `project(status, last_opened_at DESC, id DESC)`；`project(owner_id)`。
- `project_tag(project_id, tag)` 唯一索引；`project_tag(tag, project_id)` 用于标签筛选。
- `project_member(project_id, user_id)` 唯一；`project_member(user_id, project_id)` 用于查询某用户加入的项目。
- `episode(project_id, number)` 唯一，集序号在事务中分配。
- `shot(episode_id, number)` 唯一，镜号在事务中分配。
- `asset(project_id, type, name)` 或等价的归属范围唯一性实现。
- `job(status, queued_at)`、`job(project_id, queued_at DESC)`、`job(shot_id)`、`job(task_id)`、`job(idempotency_key)`。
- `review(project_id, status, created_at DESC)`、`review(target_type, target_id)`。
- `knowledge(project_id, category)`，需要搜索时可后续评估 SQLite FTS，但首版不额外引入复杂全文检索。

必须通过迁移/服务维护的完整性：

- 删除用户不能留下空的项目 owner。
- 删除项目清理已登记资产图片与关联行；不能删除未知文件。
- Shot 引用 Asset 的 ID 要在写入时验证同一用户可访问，删除 Asset 前检查引用。
- Review 的 target 与 version 由 Service 校验存在性/归属。
- `last_opened_at` 更新不能触发 `updated_at` 变更。
- 跨表派生计数尽可能查询聚合，不把派生值当权威持久列。

## 11. 必须从现有仓库核对的内容

下列项目不能由 AI 根据本文件臆造，必须检查真实代码：

3. 当前所有 `/api` 端点路径、HTTP method、请求/响应 schema、状态码和权限装饰器。
4. `asset` 如何保存参考图路径，实际目录清理规则。
5. `episode.status` 的允许值、`shot` 当前列、`asset_ids` 的存储形式。
6. `provider_config` 真实十行结构、默认选择规则、环境变量命名。
7. 当前是否已存在 document/job/task/review/knowledge/extraction 表；禁止重复创建语义相同的表。

9. 现有真实测试覆盖；不能只按设计稿的修订记录声称测试已经通过。

## 12. 数据字典变更流程

新增字段/表必须同时提交：

- migration SQL；
- Repository 映射；
- Pydantic schema；
- API/OpenAPI 更新；
- 数据回填与默认值规则；
- `PRAGMA foreign_key_check` 结果；
- 对应功能/权限/API/浏览器测试；

禁止直接修改既有迁移文件来改变已经部署的数据库；如必须修正旧迁移，先说明是否会影响空库/已有库，并优先增加前向迁移。
