# AI 视频生产平台需求概要说明书

- 文档类型：产品需求与交互规范（PRD）
- 依据：用户提供的《设计稿.md》，版本记录至 v0.58（2026-10-31）
- 面向对象：产品/设计/后端/前端/测试，以及负责编码实现的 Qwen 3.8 Flash
- 目标形态：小团队局域网部署的本地 Web 应用
- 规范用词：**必须**=验收门槛；**应**=默认要求，确有原因才能偏离；**建议**=本规范的设计补充；**待核实**=必须检查现有代码/迁移/测试，不能凭空假定

## 1. 产品定位与设计目标

### 1.1 产品定位

构建一套面向 2–5 人小团队的 AI 视频生产平台，覆盖“项目组织 → 世界观/资产准备 → 小说与剧本创作 → 分镜拆解 → 图像/视频生成 → 配音/配乐 → 自动校验与人工审核 → 素材交付”的全过程。平台本身是**生产流程编排与资料管理系统**，模型通过适配器调用现有 CLI 或国内云端 API 执行；平台不自研推理引擎，也不做在线剪辑软件。

### 1.2 已确认的产品基线

1. 本地 Web，局域网自部署，目标运行设备为 Mac Studio M5 Ultra 96GB；Windows PC 远程参与生成的协议暂不纳入本轮承诺。
2. 前端采用静态 HTML/CSS/原生 ES Module；后端 FastAPI 只提供 `/api` JSON，不在 Python 路由中拼接 HTML。不得自行引入 Node 构建链、React/Next.js 或 Jinja2/HTMX。
3. 数据库采用 SQLite WAL、版本化迁移、Repository 数据访问层；路由层禁止直接写 SQL。
4. 小说、剧本、分镜正文等文件资产保存在文件系统并由 Git 管理；SQLite 保存元数据、状态、关系、生成作业和成本。不得把正文整体迁入数据库。
5. 每个业务对象只有一个模块有写权限；其他模块只读展示、引用或跳转到对象所属模块。
6. 生成中心是唯一生成队列、Job 状态和成本账的写入口；音频中心不能创建第二条队列。
7. 审核中心是校验结果与人工签字的唯一写入口；创作中心和生成中心只读展示审核状态。
8. 默认本地优先；云端模型只使用国内厂商。云端必须由用户在具体镜头/作业上明确勾选，不允许系统因本地慢、失败或质量判定而静默切云。
9. 账号口令登录，无自助注册。超级用户由本机引导/环境变量初始化，明文口令不得写入文档或数据库；会话默认 12 小时，首次登录强制改密。
10. 明确暂不做：ComfyUI 式节点画布、在线时间线剪辑、多租户、SaaS 计费和对外服务。

### 1.3 设计补充的原则

- 先把“数据归属、状态、权限、错误和验收”写清楚，再写 UI；不得先做漂亮的孤立页面。
- 页面主要服务桌面端密集生产工作流。表格优先用于分镜、任务和审核；卡片只用于封面/缩略图/概览，不把每条记录都做成大卡片。
- 任何长任务必须异步执行，前端可离开当前页，回到生成中心仍可查看状态。
- 所有 AI 生成结果都可追溯至输入提示词、模型、参数、引用资产、执行方式和产物文件；不要求第一版做复杂的全链路审计日志。
- 失败必须可理解、可恢复；不得只向用户显示 Python traceback 或空白页面。

## 2. 目标用户与权限语义

### 2.1 角色

| 角色 | 定位 | 典型行为 |
|---|---|---|
| `superadmin`（超级用户） | 系统救援与全局维护账号，不是普通角色权限的组合 | 全部权限；不可经普通用户页面停用、改角色或重置其口令；口令恢复走 `backend/reset_password.py` 或当前已定的安全恢复流程 |
| `admin`（管理员角色） | 维护用户/角色、模型配置、管理项目 | 可访问全局项目与系统设置；受超管账号可见性规则约束 |
| `editor`（制作/编辑） | 日常制作 | 按既有 20 权限点控制，且必须具有项目成员/所有权访问资格 |
| `viewer`（只读） | 查看项目进度、文档/资产/生成和审核状态 | 只能访问权限允许且项目对其可见的数据，不得绕过 API 写入 |

**重要：** 实际系统已有 20 个 `Permission` 权限点和既定角色映射。开发时必须从当前 `bootstrap.py`、权限 seed、迁移及路由声明中读取真实代码，不得根据本文件重新发明或替换已有权限点名称。新增权限若有必要，先提出差异清单与迁移方案。

### 2.2 双层鉴权

所有业务请求必须同时通过：

1. 全局权限点校验，例如是否具备某类读/写能力。
2. 项目可见性/归属校验：管理员或项目所有人/协作人按规则访问；其他人不能通过猜 ID 访问。

规则：看不见的项目返回 404，不能透露项目存在；对看得见但不满足操作级别的请求返回 403。批量端点逐项校验并返回 `done/skipped`，不得因为其中一项失败而放宽权限或把整批不必要地全部回滚。

账号管理必须保留既有安全约束：不能停用自己；不能修改自己的角色；超级用户账号在普通用户管理 API 中只读；用户列表按层级过滤（超级用户层级 2、管理员层级 1、其他层级 0），对高于当前用户层级的目标账号写操作返回 404；删账号前必须转移其项目所有权或明确选择同时删除项目。

## 3. 信息架构与导航

### 3.1 主导航

主导航固定为以下 7 个业务模块和一个工具入口：

1. 项目中心
2. 资产中心
3. 创作中心
4. 生成中心
5. 音频中心
6. 审核中心
7. 设定中心
8. 系统设置（工具模块，不计入七个业务模块）

模块名称使用上述四字名称，不加序号。设定中心与系统设置不得混用概念：设定中心管理作品知识，系统设置管理账号/角色/权限与运行时模型配置。代码文件命名按职责使用 `knowledge.js` 与 `system-config.js`，避免 `setting.js/settings.js` 近似命名。

### 3.2 全站框架布局

- **左侧侧栏：** 桌面默认约 246px；用线性 SVG 图标、模块文字、明确的选中状态。窄屏可缩成图标栏，但不得隐藏关键入口；键盘焦点必须可见。
- **顶栏：** 左侧显示当前项目名称/面包屑与常驻下拉箭头；中间或剩余空间用于当前模块标题/辅助信息；右侧显示主题切换、用户菜单。不要在模块页重复显示一遍“当前项目 X”。
- **内容区域：** 与顶栏内层对齐，最大宽度约 1440px，使用统一的间距、标题层级、表单栅格和空态样式。
- **两套主题：** 白天“极光玻璃”、夜间“暗金片场”，共用同一 DOM 结构；CSS 色彩/圆角/阴影集中到主题 token，不在组件中零散写死颜色。用户手动选过主题后持久化；否则按本机时间 06:00–18:00 使用白天主题。
- **交互一致性：** 下拉箭头与可点击入口常驻可见；状态标签若可筛选必须是实际 `<button>`；复选框统一圆形样式；所有弹窗支持 Escape 关闭（危险确认/正在提交场景另行说明）；按钮有 hover/focus/disabled/loading 状态。
- **可访问性：** 支持 Tab、Shift+Tab、Enter、Space、Escape、箭头键（自绘菜单/列表场景）；`focus-visible` 明显；遵守 `prefers-reduced-motion`；正文不低于设计稿既定下限，弱对比文字不得低于 WCAG AA 的相应要求。
- **状态表现：** 所有异步页面统一有加载态、空态、错误态、成功反馈；表单错误就近显示在控件列，而不是跳到字段名列或仅使用浏览器 alert。

## 4. 模块需求与布局规范

## 4.1 项目中心

### 职责

只维护 `Project`、项目标签、所有人与协作人、项目状态及项目级统计。项目中心不创建/删除集、不编辑文档正文、不维护生成成本明细。

### 布局

1. 页面标题与“新建项目”主按钮。
2. 单行筛选工具条：状态 chip（在产/已归档/全部）、标签 chip、搜索框。
3. 项目表格。列建议为：选择框、项目名称/介绍、内容摘要（N 集 · N 镜 · N 资产 + 已定稿 N/M 集）、所有人、最后打开、最后修改、状态、操作。
4. 项目行点击可切换当前项目；操作按钮为“修改”“成员”“删除”。需避免点击行内按钮冒泡后也切换项目。
5. 多选后显示批量工具条：归档、恢复、追加标签、删除。批量结果在表格上方的持久结果条显示，不用 alert。
6. 新建/修改使用统一弹窗；字段顺序：项目名称、标签、项目介绍、协作人（新建可同时选协作人）；字段名置左、控件置右，控件列最大约 620px。多行字段名贴顶，单行字段名与输入控件垂直居中。
7. 成员弹窗显示所有人（只读）与协作人列表，允许有权限的人添加/移除协作人和转移所有权。无可邀请用户时显示对齐于控件列的说明文字。

### 行为规则

- 默认只显示 `active` 项目；状态筛选为在产/已归档/全部。归档项目从顶栏当前项目选择器中排除，但可在归档/全部列表找回。
- 排序：`last_opened_at` 非空优先，再按时间倒序，再按 ID 倒序；从未打开的项目沉底但不隐藏。
- 打开项目更新 `last_opened_at`，不得更新 `updated_at`。真正内容变更才更新 `updated_at`。
- 创建项目需要名称，介绍可为空但有长度上限（设计稿记录为 500 字），标签去重且最多 10 个、单标签最多 20 字；协作人一次提交。
- 修改项目名称/介绍/标签使用一个整体表单一次 PUT；不要让同一字段在不同入口分头写入。
- 归档是可逆状态，不等于删除。删除是硬删除，必须输入项目名确认；批量删除必须输入固定确认词“批量删除”。
- 批量请求逐项授权：成功项写入，失败项放在 `skipped` 且说明原因；不能将不可见对象从 404 改成 403。
- 搜索词与筛选状态跨局部重绘保存；筛选导致行不可见时，必须同步移除那些行的勾选，保证“被选中的行 = 当前可见且被勾选的行”。
- 当前项目被删除或无有效当前项目时，回退到第一个在产项目；如果只剩归档项目，当前项目置空，不要自动选中归档项目。
- 删除用户前必须明确转移名下项目，或勾选同时删除项目；不可留下悬空 `owner_id`。

### 验收

- 状态、标签、搜索可以叠加且关键词不会因点筛选 chip 丢失。
- 表头全选/半选/单行选择三者始终同步，筛选后隐藏的选择会清除。
- 归档与恢复可逆，顶栏不显示归档项目，项目仍可恢复。
- 删除需输入确认，服务端仍重新校验权限。
- 批量部分成功可显示成功数、跳过数及逐项原因。
- 项目创建和修改后介绍/标签/时间显示与数据库一致。

## 4.2 资产中心

### 职责

资产中心是角色（Character）、场景（Scene）、道具（Prop）资产的唯一写入模块；管理参考/定妆图、视觉描述、一致性提示词、设定条目引用和跨项目复用。

### 布局

1. 顶部标题 +“新建资产”按钮。
2. 筛选条：资产类型、当前项目/全局资产范围、关键词；支持按名称/描述搜索。
3. 主区采用密集表格/紧凑列表，列包含缩略图、名称、类型、归属（当前项目/全局）、更新时间、操作。不要默认把所有资产渲染成大卡片墙。
4. 新建/编辑用统一弹窗或左右主从布局：基本资料字段、视觉描述、一致性提示词、引用设定条目、参考图上传/预览。
5. 参考图点击可看大图；删除按钮清晰但避免误触；无图时显示显式上传按钮。
6. 全局资产可标记“全局”并由有权限的人管理；项目引用不复制资产内容。

### 功能

- 创建、编辑、查询、删除角色/场景/道具。
- 资产名称在同一归属范围与同一类型下必须唯一；冲突返回 409，并在界面显示可理解的提示。
- 上传参考图只接受 PNG/JPEG/WebP，最大 20MB；检查文件实际签名，不仅依赖 Content-Type；HEIC 给出格式转换提示。
- 文件按资产 ID 与随机文件名存于数据目录，前端只使用服务端返回的安全相对路径/资源 URL，不接受用户任意磁盘绝对路径。
- 删除图片时必须校验图片确属该资产；删除资产时只清理数据库明确登记的图片文件与空目录，不删除目录里的未知文件。
- 资产可以引用 `Knowledge`，并可以被多个镜头引用。跨项目复用时保存引用关系，不复制并产生冲突的第二份内容。
- 镜头上只显示资产 chips 与跳转入口，不在分镜页内修改资产内容。

### 验收

- 类型、名称、范围筛选正常；重名准确返回并展示冲突原因。
- 上传格式/大小/签名校验正常；路径穿越和任意路径删除被拒绝。
- 资产更新后，所有引用该资产的镜头可以读到最新资产信息。
- 删除项目/资产时图片清理精准；未知文件不会被一并删除。

## 4.3 创作中心

### 职责

管理 Episode（集）、Doc（小说/剧本/分镜文档元数据与状态）、Shot（镜头表格）、AI 文本创作操作与资产引用。文档正文仍然落在文件系统/Git 中。

### 布局

- **左侧树：** 当前项目 → 集 → 文档（小说/剧本/分镜）；建集、重命名、删除集仅在这里发生。
- **中间主区：** 根据选中节点显示文档编辑器或分镜表格。小说/剧本建议提供正文查看/编辑区域、保存/润色/版本操作；分镜用密集表格而非节点图或卡片画布。
- **右侧上下文区（可折叠）：** 资产引用、知识条目引用、当前文档状态、AI 操作参数/结果。窄屏时转为抽屉，避免三栏挤坏编辑区。
- **分镜表格：** 序号、场景/画面描述、景别、镜头运动、时长、对白/旁白、图像提示词、视频提示词、引用资产、最新生成状态、审核状态、操作。字段必须根据当前数据库已存在列做兼容；新增列通过迁移添加。
- **AI 工具栏：** 起草、扩写、续写、润色、压缩、改写语气、扩展灵感、生成剧情大纲、剧本化、生成分镜建议、生成提示词、从文档抽取角色/场景/道具候选。

### AI 创作与提示词生成的明确行为

- 每个 AI 操作先由用户选择范围（当前段落/当前文档/当前集/选中的镜头）、目标与约束；如果范围不明确，不允许默认把整篇正文提交给模型。
- 灵感扩展至少支持：继续给出情节方向、冲突升级、人物动机、场景变体、结尾悬念。候选以列表展示，用户选择后才并入正式文档。
- 小说/剧本润色需保留用户明确要求不变的角色名、世界观规则、事件顺序、已定稿台词/术语；用户可填写“必须保留/禁止改变”约束。AI 输出先放暂存区，默认不直接覆盖原文。
- 剧本化输出结构化字段：场景标识/内外景与时间、出场人物、动作、对白/旁白、情绪/节奏提示；不满足格式时允许人工编辑，不可将自由散文直接当作结构化剧本成功。
- 分镜建议以一行一个镜头输出，镜头描述可补充景别、机位/运动、建议时长、对白引用、可视化信息和负面约束；用户确认后才写入 Shot。
- **提示词生成器至少支持图像与视频两种目标。** 输入包括镜头描述、引用资产的一致性提示词、设定约束、目标模型档位/能力、画幅/分辨率/时长等适用参数；输出包括主提示词、负面提示词（若模型支持）、必要的分段/镜头运动描述、被引用资产清单、模型适配注意事项。模型不支持的参数不应显示为可提交字段。
- 提示词必须能预览、编辑、复制；经用户确认后才写入分镜字段/生成 Job。提示词生成本身若调用 LLM 也要创建文本 Job，保留输入/输出快照和成本。
- 提示词模板可以按能力、风格、镜头类型、模型档位检索和复用；模板只提供文本与参数默认值，不保存任意 shell 命令。模板的建议数据结构见系统设计与数据字典。
- AI 生成结果需要标明使用模型及生成时间；若模型调用失败，保留输入/错误与可重试入口，但不生成“假完成”文档或镜头。

### 文档与版本规则

- 文档类型固定至少三类：`novel`、`script`、`storyboard`。正文文件路径受平台配置的工作区根路径约束，不允许任意路径读取/写入。
- 状态流建议为 `draft → polishing → finalized`，其中 `polishing` 可由任务驱动；需要退回时必须有明确“退回草稿”操作。不能在没有写入正文的情况下把状态假装为定稿。
- 写入正文成功后才提交 Git；失败时不得留下“状态已更新但正文未写入”的半状态。Git commit 要记录可识别的操作说明和文档路径，不将密钥写入提交内容。
- 同一文件采用占用标记/编辑锁，记录 holder 与时间。掉线锁必须可过期清理；保存时使用版本/更新时间校验，防止静默覆盖他人修改。
- 任何 AI 润色默认生成可预览的修改结果；用户确认应用后才覆盖正式文档（可设置是否允许“一键应用”，但默认不直接覆盖）。采用 diff/版本对比，提交后可从 Git 查看版本。
- 分集状态当前已有 `done` 用于“已定稿 N/M 集”计数。推荐完整显示 `draft/in_progress/done`，但在修改已有枚举前必须检查当前 `PATCH /api/episodes/{id}/status` 校验白名单和已有数据，写迁移/兼容策略。

### 分镜/资产引用

- 镜头引用资产是引用关系，不拷贝角色文本/图片；页面显示资产名、类型、必要时显示参考图缩略图。
- 镜头引用变更只在创作中心通过选择器更新 `Shot.asset_ids` 或现有等价字段；但不得从该页面编辑 Asset 内容。
- 删除仍被引用的资产时，必须明确行为：推荐先拦截并给出引用镜头列表；若项目级联删除场景另走已确认的项目删除流程。不可留下悬空 ID。

### 文本抽取

- 文档抽取人物、场景、道具等候选时必须保留原文偏移/证据片段，不得只把模型归纳结果无依据地直接入库。
- v1 只允许角色/场景/道具候选经人工确认入资产库；镜头候选先导出 Markdown，不直接批量写入 shot。
- 抽取任务走生成中心统一 Job/成本入口；建议具备幂等键，重复提交相同文档版本与抽取参数不应重复落入资产库。

### 验收

- 能在创作中心创建/删除集；项目中心只读显示集计数。
- 小说/剧本文档写入文件，Git 有对应提交；能查看历史与差异。
- 一次润色流程完成：运行脚本/模型、展示差异、用户确认、写回、Git 提交、产生校验报告。
- 分镜每条能保存、引用资产、提交生成作业；资产内容只能在资产中心改。
- 并发编辑被明确阻止或要求合并，不允许静默丢失修改。

## 4.4 生成中心

### 职责

唯一生成队列、生成 Job、模型路由、参数模板、日志/产物、重试/取消与成本账。任何由创作、音频、抽取等功能发起的实际生成，最终都进入本模块的 `job` 队列。

### 布局

1. 顶部为队列概览：等待、运行、成功、失败、需处理数；成本显示按当前项目/时间范围筛选。
2. 筛选栏：任务能力（文本/图像/视频/TTS/音乐/抽取）、状态、执行方式（本地/云端）、模型、项目/集、提交时间。
3. 主表格：状态、任务名/镜头、能力、执行方式、模型/适配器、提交/开始/结束时间、耗时、成本、操作。
4. 选中 Job 展开右侧详情/抽屉：输入摘要、完整参数、提示词、引用资产、日志、错误原因、产物文件、成本计算、重试/取消操作。
5. 成本账页/区块必须位于生成中心；项目中心只读展示累计成本摘要。

### Job 功能

- 从分镜一键提交文本到视频（T2V）、参考图到视频（I2V）、图像生成、配音、音乐、文本润色/抽取等。
- 统一状态建议为 `queued`、`starting`、`running`、`succeeded`、`failed`、`cancel_requested`、`cancelled`、`needs_attention`。现有代码若采用别的状态，需要先映射，不得并存两套状态机。
- 每个 Job 保存能力、执行方式、本地/云端提供方、模型、适配器版本、参数快照、提示词快照、输入引用、输出文件、日志路径、错误代码/摘要、时间字段、重试次数和成本快照。
- 本地生成串行运行，同时最多一个本地生成任务；云端 API 可按限流策略并发提交，但数据库状态写入由平台统一管理。
- worker 必须是与 API 请求处理隔离的独立子进程/执行进程；请求接口只入队并快速返回，不等待模型跑完。队列持久化在 SQLite，服务重启后能够恢复未开始任务，并将“执行中但 worker 已消失”的任务标为可恢复的失败/待重试状态。
- 模型适配器只做薄包装：构造 CLI 参数、启动子进程、收集退出码/日志、定位产物。已有脚本继续可在终端独立执行；不得把推理代码重写进 FastAPI。
- 默认本地优先。对于视频任务，T2V 的本地默认路线为 FastMetal；I2V/大模型档按已确认参数走 mlx-video；图像走 mflux；TTS 走 VoxCPM2；音乐走 ACE-Step。具体可用档必须以机上基准结果和可运行配置为准。
- 云端选项只允许已配置的国内供应商。每一个镜头/作业都需要用户显式选择云端并确认预计单价/成本提醒；系统不得自动从本地失败切换到云端。
- 记录云端请求 ID、供应商响应摘要与计价量，密钥永远不写 Job 参数、日志、错误或 API 响应。
- 失败后用户可在查看错误与参数后重试；重试生成新 Job 记录，关联原 Job，不要覆写原失败的日志/成本。若供应商已产生费用但平台未收到结果，需保留“成本/结果待核对”状态，不可假装零成本。
- 本地成本可以金额为 0，但仍保存耗时/资源指标；云端成本按提交时价格表/用户确认的单价和计量单位记录快照。
- 多币种成本不直接相加；按币种分组展示。如未来要折算统一币种，必须保存汇率与换算时点，作为新需求。
- 加速参数只显示当前适配器/模型真实支持的参数，不能把 5B 专有的开关显示给 1.3B。模型启动失败不得让 UI/API 进程退出。

### 参数模板

- 可保存具名模板（能力、模型/适配器、参数 JSON、适用分辨率/帧数、默认标志、创建/更新时间）。
- 模板是参数预设，不是可执行任意命令；命令二进制与允许参数必须由服务器端 adapter 白名单决定。
- Job 提交时冻结参数快照，之后修改模板不能改变已创建 Job。

### 成本规则

- 唯一口径：`cost_amount = unit_price × quantity`，以 Job 提交时保存的单价、数量、单位、币种为准；金额/成本不能在项目中心手动编辑。
- 失败 Job 的费用应按供应商真实返回/计费情况记录；不能因为 `status=failed` 自动归零。
- 项目成本是 Job 的聚合只读值；未产生金额的本地任务可显示 0 元及其耗时。

### 验收

- 页面提交请求立即返回 Job ID，UI 在作业执行几十分钟时仍可切页/刷新。
- 1 个本地 Worker 串行执行，无两个本地任务同时抢占模型内存。
- 视频 T2V 可调用 FastMetal、I2V 可调用 mlx-video；图像、TTS、音乐适配器可分别端到端运行后再开放对应功能。
- 失败、取消、重试、服务重启恢复状态可测试；日志不会输出密钥。
- 成本记录可与一笔已知云端供应商账单或手工算式核对。

## 4.5 音频中心

### 职责

管理对白与旁白文本关联、声音生成素材、音乐条目及口型 viseme 数据。**它不运行独立队列、不记成本。**

### 布局与功能

- 建议采用三个二级页/标签：对白与配音、音乐素材、口型数据；具体可复用模块原有二级导航模式，但不额外放一个“任务队列”页。
- 对白与配音列表列出集/镜头、说话人、台词、语言/音色、生成音频、字级时间戳、当前状态及“送进生成队列”按钮。
- 配音配置包含声音/说话人标识、语速/音调/可用参数；只展示适配器支持字段。VoxCPM2 的字级时间戳和拼音覆音按实际 CLI 输出映射。
- 音乐条目支持名称、风格/情绪、提示词、时长、参考文件、生成文件、归属项目/集；生成动作交生成中心。
- 口型数据通过 viseme 时间序列挂接到对应音频/镜头；Rhubarb 数据只在需要口型特写的任务保留，不得默认为所有镜头制造无用文件。
- 对白镜头默认本地 VoxCPM2 + Rhubarb；云端音画同生可用，但必须明确接受模型自带音色/音轨与既有定稿对白配音之间的权衡。不能把“模型原生音轨”和“VoxCPM2 最终配音”假设为天然同步。
- 非对白空镜/环境声可实验本地 FastH3 原生音轨；此能力在未完成试听与质量评估之前应标为实验选项，不作为确定交付承诺。
- 音效补声路线（MMAudio / stable-audio-open 等）属于待验证项；在适配器、权重、许可证、成本/耗时没有确认之前不得假装已支持。

### 验收

- 音频中心可查看、组织、引用配音/音乐素材。
- 点击生成只创建生成中心的 Job；本模块不维护单独状态机或队列。
- 生成音频与镜头/对白关联准确，任务进度和成本由生成中心读取。

## 4.6 审核中心

### 职责

自动校验门禁、人工审核队列、审核意见/结果和签字记录的唯一入口。

### 布局

- 顶部筛选：待处理、通过、未通过；目标类型（文档/Job/镜头）；gate 类型（自动校验/人工审核）；集/时间筛选。
- 主区为审核任务表格：对象、当前版本/Job、检查项、状态、提交时间、待处理时长、操作。
- 选择一项后使用主从布局：左/中区查看文档或媒体/日志，右侧显示校验报告、问题列表、审核意见、通过/驳回/退回操作。
- 人工签字需明确显示审核对象、版本/Job ID、签字人、签字时间、结果与意见。必须让签字对象不可歧义，不可对“最新文档”签字却不冻结其版本。

### 功能

- 用统一封装调用现有校验器脚本；输出结构化报告（检查项、结果、严重级别、消息、定位信息、时间）。
- gate 可挂在 Doc 或 Job 上；同一对象可有多个不同 gate 的记录，但一份 Review 记录只能对应一个明确目标和版本。
- 审核者可以通过、驳回或退回修改；驳回/退回必须填写原因。通过后保存签字记录。
- 任意其他模块只显示审核状态和跳转，不提供写 Review 的按钮/接口。
- 对逐句签字场景，必须有可枚举的句子/条目锚点（例如文档路径+Git commit+行/段落标识）；如果目前已有校验器输出格式不足，列为明确 API/数据扩展任务。
- 自动校验通过不等同人工签字通过；两个状态要独立记录。

### 验收

- 审核结果只能通过审核中心 API 创建/更新。
- 审核记录绑定的具体版本或 Job 快照可回溯。
- 通过、驳回、退回都产生持久化记录；非审核角色不可签字。

## 4.7 设定中心

### 职责

世界观、人物关系/历史背景/规则等业务知识条目，以及来源证据快照的唯一写入模块；项目级与全局两种范围。

### 布局与功能

- 左侧可按“全局设定/当前项目”切范围；主区显示条目表格（标题、类别、摘要、范围、最近更新）；详情区编辑正文、标签和证据引用。
- 条目支持创建、编辑、搜索、标签、归档/删除策略（建议优先归档，是否硬删需有引用检查）。
- 证据快照保存文件引用、来源名称/日期、摘录/摘要、必要时的页码或段落定位；来源内容应留在本地资料目录，平台保存可复现的路径和引用元数据。
- 创作中心可读引用设定条目，但只能跳转至设定中心修改。
- 全局条目必须有明确授权策略；项目协作者不能通过引用关系修改全局内容。

### 验收

- 项目设定与全局设定能区分；授权不串项目。
- 创作文档引用条目后可以跳转；条目更新不会改写原始文档正文。

## 4.8 系统设置

### 4.8.1 用户与角色

- 用户表：用户名、显示名、角色、启用状态、最后登录时间；禁止显示密码哈希、会话令牌和初始明文口令。
- 操作：新建用户、启用/停用、重置口令、改角色、删除用户。
- 新建用户填写用户名、显示名、一次性初始口令/重置流程与角色；首次登录强制改密。
- 删除用户必须选择转移所有项目给另一个有效用户，或连同其项目一起删除；有名下项目时不允许静默删除。
- 权限矩阵显示既有 20 权限点 × 3 角色；admin 角色列按既定规则禁用编辑。具体权限点名称来自现有 seed，不能被新文档重新命名。
- 系统设置侧栏入口在 `system:config` 或 `user:read` 任一权限满足时可见；进入子页后仍分别授权，不能因为可查看用户就自动能编辑模型密钥。

### 4.8.2 模型与密钥

- 固定五类能力：文本、图像、视频、TTS、音乐；配置覆盖本地与云端执行方案，共 10 个能力/执行方式配置槽位。
- 配置 provider 标识、模型标识、默认/启用状态、允许参数/能力、环境变量密钥名、健康状态与备注。密钥值只通过 `FV_KEY_<PROVIDER>` 等环境变量读，禁止落库/回传/渲染/写入日志。
- 页面只显示“已配置/未配置”，不得返回密钥的部分明文或完整值。
- 文本 LLM 的云端端点只允许国内厂商（设计稿建议火山方舟或 MiniMax，最终以环境变量及当前可用性为准）。视频云端候选包括设计稿列出的国内服务商，但正式启用前必须复核模型名、API 版本、计价单位、服务协议和许可证。
- 模型默认策略：图像、视频、TTS、音乐默认本地；文本 LLM 需配置受允许的国内云端端点。云端视频必须逐镜头显式选择，不能因为配置了云端就自动使用。
- 对模型能力的真实支持要由 adapter manifest 或服务端白名单驱动；UI 不手写模型参数的假支持。

### 验收

- 密钥从未出现在数据库内容、前端响应、日志、错误提示或 Git。
- 只有具备相应配置权限的人可以修改 provider；普通模块只能读取当前默认模型/状态。
- 新增 provider 不需要复制一套队列或成本逻辑，而是实现统一 adapter contract。

## 5. 共通业务流程

### 5.1 从灵感到视频的主流程

1. 项目中心创建项目，并确定所有人/协作人。
2. 设定中心创建世界观/背景资料；资产中心创建角色/场景/道具与参考图。
3. 创作中心创建集，生成或导入小说，使用 AI 起草/润色；保存前预览差异，确认后写入文件并 Git 提交。
4. 创作中心生成/维护剧本，并将场景拆分为结构化分镜。镜头引用资产和设定条目。
5. 对文档运行校验；审核中心接收自动校验结果，必要时人工审核/签字。
6. 从镜头表选择任务类型、模型档位、参数模板；默认本地。确实需要云端时用户勾选镜头并确认供应商、单价与风险。
7. 生成中心创建 Job、入队、执行、记录日志/产物/成本；前端轮询或刷新读取状态。
8. 音频中心整理对白/旁白/音乐，将生成请求交给同一生成中心队列，获得素材后关联至镜头。
9. 审核中心校验生成结果，标记通过/退回；创作中心/项目中心只读展示进度。
10. 下载/导出素材供外部剪映/达芬奇后期，不在平台中剪辑。

### 5.2 AI 润色/写回流程

1. 锁定目标文档当前版本（文件路径 + Git commit/文件哈希）。
2. 提交文本 Job，保存输入文本版本、提示词、模型和参数快照。
3. 输出到暂存文件/临时结果，不覆盖正文。
4. 用户比较差异并确认应用。
5. 写入目标文件并成功 Git commit；状态更新与 commit 结果需保持一致或提供补偿恢复。
6. 运行校验器，生成 Review/gate 记录。
7. 失败任何一步时保留原文与 Job 日志，提示用户从哪步恢复。

### 5.3 文本抽取流程

1. 选择文档版本与抽取范围。
2. 创建 extraction Job，模型从正文提取角色/场景/道具候选。
3. 每条候选包括类型、建议名称、描述、原文起止偏移、证据文本、抽取 Job/模型、置信度（仅作辅助，不作自动通过依据）。
4. 用户逐条接受、编辑后入 Asset，或忽略；重复候选按幂等键/同类同名规则处理。
5. 镜头候选只导出 Markdown，不自动写入分镜表（v1 范围）。

## 6. 全局交互与状态规范

- **请求状态：** 按钮点击后立即显示 loading/禁用，成功后更新相关区域；避免整页重新渲染导致输入丢失或原生复选框状态闪退。
- **列表局部刷新：** 筛选 chip 点击只更新筛选区与列表，不重建无关输入框；所有筛选状态由模块级 state 统一持有。
- **表单：** 标签在输入控件上方或左栏，统一对齐；验证错误靠近字段；支持取消与 Escape；保存中重复提交要禁用。
- **危险操作：** 删除/清理资产、删除项目、批量删除必须明确对象和影响范围；后端再次校验权限和确认词。
- **空态：** 空态明确说明原因与可执行的下一步；不把用户带到重复写入口。例如创作中心没有集时在本模块创建集，不再引导去项目中心。
- **文件路径：** UI 只处理 API 返回的相对资源 URL，不直接拼任意服务器路径。
- **局部数据一致性：** 更新一个对象后，当前页面相关的派生计数和跨模块只读状态要刷新；避免把“最后打开”错误计为“最后修改”。
- **可观测性：** 对长任务展示可理解状态，不假装所有模型都能提供百分比进度；若底层脚本没有百分比，则显示“运行中/已运行时长/阶段日志”。

## 7. 非功能需求

### 7.1 性能与容量

- 目标规模为 2–5 名局域网用户、万级任务记录；SQLite WAL 为默认方案，暂不预设 PostgreSQL。
- 长视频生成期间浏览器操作、API 查询与用户管理不应被阻塞。
- 本地生成同一时刻最多一个任务；默认逐任务加载/释放模型，常驻模型开关默认关闭。
- 项目列表聚合统计尽量通过一次查询/聚合返回，不为每一行发起额外网络请求。

### 7.2 安全

- 所有业务端点明确声明权限；不依赖前端隐藏按钮实现授权。
- cookie 会话 HttpOnly、SameSite=Lax；生产配置下仅允许白名单 CORS，默认关闭跨域。
- 所有模型密钥从环境变量读取并遮蔽；命令行、异常与日志对密钥/授权头脱敏。
- 上传文件校验扩展名、文件签名、大小；防路径穿越和任意文件删除。
- 文件访问限定在配置的工作区/数据目录内，禁止 `..`、符号链接绕过与任意绝对路径。
- 删除项目、用户、资产要在事务和文件清理策略中定义失败补偿；优先先收集清单，数据库提交后再删除文件或采用可恢复的删除清单，避免数据库已删而实际文件清理失败却无记录。
- 不把账号口令、API Key、完整环境变量或个人文件路径写进需求文档/提交记录。

### 7.3 可维护性

- SQLite 结构只能通过版本化迁移更改；每个迁移事务独立，启动时执行迁移前自动备份现有数据库，保留最近 5 份（已有逻辑需核实）。
- 所有 SQL 位于 Repository 层；业务逻辑位于 services/access 层；Router 做校验、调用服务并返回响应，不跨 Router 相互导入。
- CLI 适配器可独立从终端复现；平台不修改第三方脚本的核心行为。
- 业务功能只保留一个写入入口；共同组件（弹窗、表格、表单提示、状态标签、请求错误处理）统一。

### 7.4 兼容和迁移

- 新增字段需有向前迁移与旧数据回填策略；已有 API 路径/状态在非必要时保持兼容。
- 如果发现设计文档与当前源码有差异，先记录为 `SPEC-DIFF`：现状、依据、目标、迁移、回归测试；不可整体重写覆盖已有实现。

## 8. 四期功能融合后的范围与优先级

本节描述**完整产品目标**。即使实现按四期交付，功能边界也要按完整产品来设计，避免四期互相拆出重复入口。

### P0：平台和对象基础（一期基础）

- 登录/登出/当前用户/修改密码/强制改密；账号、角色和权限管理；项目所有权和项目成员检查。
- 项目创建、编辑、列表/筛选/归档/批量操作/硬删除确认/所有权转移。
- 集、资产、参考图、基础文档文件管理、Git 提交、编辑占用标记。
- 系统设置的本地/云端双轨 Provider 配置页（密钥值不入库）。
- 通用布局、主题、请求错误处理、迁移/Repository/备份。

### P1：生成闭环（二期核心）

- Job/Task 状态与 SQLite 持久队列；独立 worker；日志、失败恢复、取消/重试。
- Model adapter contract；FastMetal T2V、mlx-video I2V、mflux 图像、文本 LLM（国内 API）接入；云端视频 provider 按显式选择启用。
- 参数模板、输入/参数快照、产物登记、成本记账、项目只读成本汇总。
- 机上模型基准测试，把耗时、峰值内存、质量、分辨率、帧数填回档位配置；未经实测不得伪造性能数据。

### P1：创作与审核闭环（三期核心）

- 完整 Doc 状态机、AI 起草/扩写/润色/剧本化、分镜表格、资产引用选择器。
- 文档 Git 版本/差异、占用与冲突保护。
- 文本抽取候选与证据偏移、候选审核入资产。
- 自动校验器 gate、Review 状态、人工签字、逐句签字需要的锚点。

### P2：音频与项目看板（四期核心）

- VoxCPM2 TTS、音频文件和字级时间戳；Rhubarb/viseme 与镜头挂接。
- ACE-Step 音乐生成与音乐条目管理。
- 环境音/音画同生的实验性接入必须经过单独基准和许可核查，不默认纳入 P0。
- 项目进度看板：集完成数、镜头生成状态、审核通过数、失败/待处理任务、成本摘要。
- 导出项目资产清单/镜头素材清单供外部剪辑软件使用（不实现在线剪辑时间线）。

## 9. 重要设计冲突与规范决策

| 编号 | 冲突/风险 | 本说明书的规范处理 | 实施注意 |
|---|---|---|---|
| D-01 | 设计稿一处提“同进程后台 worker”，多处要求生成 worker 独立进程 | 统一采用独立 worker 子进程；API 进程只负责入队/查询/状态编排 | 不在请求线程里生成；SQLite 队列是唯一状态源 |
| D-02 | Shot 被描述为属于 Doc（剧本），现有 API 却按 `/episodes/{id}/shots` 访问 | 先保持既有 API 与迁移的 `episode_id` 关系兼容；检查现有 schema 后，再用可选 `doc_id`/关联表表达文档关联，不破坏现有端点 | Qwen 必须先读现有 `0004_content.sql` 与 models/repositories，确认后写 `SPEC-DIFF` |
| D-03 | Doc 是九实体之一，但正文应留文件，当前初期迁移是否有完整 `doc` 表需核查 | 文件保存正文；数据库保存路径、类型、所属集、状态、Git 引用等元数据 | 若当前缺表，用增量迁移建立，不能搬正文进 DB |
| D-04 | 当前分集状态显示 `done`，但完整状态值没有在正文列明 | `done` 为必须支持值；其他状态从现有 `Literal`/模型读取。建议阶段性状态 draft/in_progress/done，但需先核对兼容 | 不直接改写已有状态枚举，新增值要有迁移/回填/测试 |
| D-05 | “五类能力 × 本地/云端”与“每种能力恰好一个默认”可能被解读为多个默认 | 每个能力应只有一个有效默认路线；日常图像/视频/TTS/音乐默认本地，文本 LLM 用允许的国内云端端点；云端视频仍需逐 Job 人工确认 | 配置页必须展示有效默认与可用性，不能静默 fallback |
| D-06 | 逐句人工签字需要识别签字人，但身份基线又倾向业务数据不引用账号 | Review 需要明确 signer 身份，建议对 Review 设唯一 `reviewer_user_id` 例外；其他业务实体不加普遍性的 created_by 审计字段 | 实施前核对现有 schema，确认是否接受此例外；不可用自由文本冒充可信身份 |
| D-07 | 资产图片路径的持久化方式未从设计稿完全确认 | 先检查当前 `asset` schema 和 `/api/assets/{id}/images` 实现；数据字典提供逻辑定义，实施时优先沿用现有字段/存储方式 | 不能引入第二套图片登记机制导致一份文件多份真相 |
| D-08 | 模型价格与单价随供应商更新，文档中有旧报价 | 所有价格视为待复核数据，运行时按提供方最新计价/用户确认值记录快照 | 不硬编码旧价格，不虚构成本与耗时 |

## 10. 不在当前范围内

- ComfyUI 式节点图工作流编辑器。
- 在线视频时间线剪辑、转场、字幕时间轴合成与最终成片渲染器。
- SaaS 多租户、自助注册、对外开放用户/计费平台。
- 将小说/剧本全文搬入 SQLite。
- 静默自动切换云端、自动将未审文本标记为定稿、自动将抽取候选直接入资产库。
- 不经真实机上测试即宣称模型的耗时/峰值/画质/帧率。
- 未确认许可、国内可用性、API 版本或计价方式的供应商，不能作为默认生产路径。

## 11. 完整验收总场景

上线前至少通过以下端到端场景：

1. 未登录访问业务 API 得到 401；健康检查不依赖登录。登录后首次改密；登出后会话立即不可用。
2. viewer 不能写项目/资产/文档/模型配置；editor 即使具有某全局权限也不能访问自己不是成员的项目；不可见项目返回 404。
3. 创建项目并邀请协作者；协作者可执行被授权的制作操作，但不能删除项目或管理成员；归档项目不会成为当前项目回退目标。
4. 创建资产、上传有效/无效格式图片、引用资产到镜头、删除图片/资产；验证拒绝越权路径和保留未知文件。
5. 小说/剧本保存成文件、Git 有提交；并发编辑能提示冲突；润色可以预览、确认写入、生成校验报告。
6. 生成中心创建一个本地视频 Job，API 快速返回；worker 串行调用指定 CLI，产物和日志落盘；失败可重试且保留原始失败记录。
7. 用户显式勾选云端镜头后，页面显示供应商/计价单位/预计成本；未经勾选，即使本地失败也不产生云端请求。
8. 成本按 Job 明细汇总，项目中心仅显示只读总览，多币种不混加。
9. 音频中心提交 TTS/音乐任务后，只在生成中心出现一个 Job；不存在第二条队列。
10. 审核中心创建自动 gate 和人工 Review；只有审核中心可签字；签字绑定具体文档 Git 版本/Job ID。
11. 迁移旧数据库后 `PRAGMA foreign_key_check` 无异常；备份可恢复；所有新功能回归现有的项目、用户、标签、归档、协作人和主题交互。

# AI 视频生产平台系统设计说明书

- 文档类型：系统架构、组件、接口、状态机、运行与测试设计
- 开发约束：先审查现有 `app/`，以增量修改方式实现；本说明不授权整体重写
- 技术基线：静态前端 + FastAPI JSON API + SQLite WAL + 文件系统/Git + CLI 适配器 + 独立 Worker

## 1. 设计目标与系统边界

系统负责账号与项目权限、业务对象元数据、文件定位、任务排队/状态、模型路由、成本记账、审核与协作 UI。模型推理由现有命令行脚本或国内供应商 API 执行。最终视频剪辑交外部剪映/达芬奇，不建设在线剪辑引擎。

核心不变量：

1. 一个业务对象只有一个模块作为写入所有者。
2. 一个生成 Job 表、一个持久化队列、一个成本计算口径。
3. 一个 Review 写入入口，即审核中心。
4. 一个配置事实来源：数据库保存配置元数据，密钥只从环境变量来。
5. 一个文档正文事实来源：文件系统/Git，数据库不存正文全文。
6. 每次跨模块调用只传资源 ID / 版本引用 / 参数快照，不复制一份可独立修改的业务对象。

## 2. 总体架构

```text
Browser
  ├─ static HTML/CSS/ES Modules
  ├─ store + router + api client + views
  └─ /api JSON + /files safe static asset URLs
            │
            ▼
FastAPI application (JSON only)
  ├─ routers/           HTTP schema, auth dependency, response
  ├─ services/          business orchestration and transaction policy
  ├─ access.py/ranks.py centralized access predicates
  ├─ repositories/      only SQL access
  ├─ adapters/          provider/CLI thin wrappers
  ├─ job dispatcher     enqueue/cancel/reconcile/status
  └─ SQLite WAL + filesystem workspace/data files/Git
            │
            ├─ independent local worker process (serial local model execution)
            │      └─ CLI subprocess: FastMetal / mlx-video / mflux / VoxCPM2 / ACE-Step / validators
            └─ Cloud adapters (domestic providers only; explicit per-job user selection)
```

### 2.1 进程隔离

设计稿对 worker 所在进程有相互冲突的两种描述。统一规范采用**独立 worker 子进程**。FastAPI 进程负责 API、队列表访问与状态协调，不执行长时间模型推理。Worker 由启动管理器/dispatcher 拉起，读取 SQLite 持久队列并启动具体 CLI 子进程。即使项目代码中当前有“同进程后台 worker”，也要先记录差异并按独立进程的目标实现迁移，不得在两个地方各保留一套调度状态。

### 2.2 目标目录结构

先检查现有目录，不要为了吻合下列示意强制重命名。目标职责建议如下：

```text
app/
  backend/
    main.py config.py db.py migrate.py bootstrap.py
    routers/                 # route 只做 HTTP 层
    repositories/            # 所有 SQL
    services/                # 删除清理、生成协调、文档/Git、校验流程
    adapters/                # text/image/video/tts/music/provider wrappers
    workers/                  # queue dispatcher / worker process / recovery
    access.py ranks.py        # 现有权限语义的单一实现
    migrations/               # 顺序迁移文件
    reset_password.py
  frontend/
    index.html css/ js/ img/
    js/views/projects.js
    js/views/assets.js
    js/views/creation.js (若现有命名不同，按当前文件映射)
    js/views/generation.js
    js/views/audio.js
    js/views/reviews.js
    js/views/knowledge.js
    js/views/system-config.js
    js/views/system-users.js
  data/                       # DB、上传文件、任务日志、生成产物
  workspace/                  # 可配置的内容根目录/Markdown + Git，不强制迁移
```

重要：已有项目版本使用原生 ES Module 和每视图一个文件；不要引入编译步骤/依赖管理新栈。如当前实际文件名不同，先产出 `CURRENT_TO_TARGET_FILE_MAP.md` 后再迁移。

## 3. 前端设计

### 3.1 通用模块

- `api client`：统一 fetch、JSON 解析、状态码、错误对象，401 触发会话失效流程，403 显示权限不足，404 按服务端语义显示对象不存在，409 显示冲突，422 显示字段错误。禁止每个 view 自己重新实现错误解析。
- `store`：当前用户、权限、项目清单、当前项目、在产项目、主题和会话状态的单一前端缓存来源。
- `router`：hash 路由/模块子页导航；无效子页索引必须归一并回写 URL，避免内容与侧栏高亮不一致。
- `modules.js`：定义导航标签、图标、子页和所需权限。权限仅用于改善 UI，真正鉴权仍在后端。
- `util.js`：统一弹窗、toast/页面错误、确认、日期格式化、转义、状态标签等。
- 视图不可通过自己的 `fetch` 或 DOM 逻辑访问业务对象的另一个模块写 API；按模块所有权划定调用。

### 3.2 页面结构准则

- 表格用于项目/任务/资产/分镜/审核/用户列表；角色、场景等需要看图时在表格中放小缩略图，点开详情。
- 使用主从布局处理复杂对象：左侧目录/筛选，中间表格或编辑器，右侧详情/引用/日志；窄屏将右侧移入抽屉。
- 不为每条记录创建独立的大卡片；首屏应优先展示高频生产动作和状态。
- 每页所有写入入口只有一个明确归属，不可在 Dashboard、摘要栏、引用 chips 中放第二个写按钮。
- 表格行内动作与行点击必须阻止事件冒泡，不能导致选择框被点击后整页刷新/切项目。
- 筛选、选择、编辑草稿状态保存在视图状态中；筛选只局部更新列表，不能清空搜索词或把隐藏行留在选择集合里。

### 3.3 页面细节

- 项目中心：单页列表，无二级“项目管理/成本账”页；状态/标签 chip 真正可键盘操作；批量结果条；项目介绍单行截断；归档提示能反向找回。
- 资产中心：当前项目与全局范围切换 + 类型/关键词筛选 + 紧凑列表/表格 + 资产编辑弹窗/详情；图片点击预览。
- 创作中心：左侧项目/集/文档树，中间正文编辑器或分镜表，右侧资产/Knowledge 引用和 AI 工具；分镜主要使用表格，不做节点画布。
- 生成中心：指标条 + 筛选 + 队列表 + Job 详情抽屉；日志/参数/成本/产物都从同一 Job 读。
- 音频中心：对白、音乐、口型数据分区；只产生“提交到生成中心”的动作，不展示独立队列状态机。
- 审核中心：待审核队列 + 对象预览/校验报告 + 审核意见与签字；签字区固定且要求确认具体版本。
- 设定中心：全局/项目范围 + 条目列表 + 正文/证据详情；不能代替资产中心编辑视觉资产。
- 系统设置：模型与密钥、用户与角色两个子页，各自二次授权；密钥永不回传。

## 4. 后端分层

### 4.1 Router

每个业务端点显式依赖具体 `require_permission(...)`，认证端点自带认证逻辑，健康检查例外。Router 负责：HTTP 输入模型校验、依赖装配、调用 Service/Repository、映射状态码和响应模型；不写 SQL、不直接调用 CLI、不自己复制项目权限判断。

### 4.2 Service

负责跨对象事务和副作用编排，如 `delete_project_cascade`、文档写入 + Git commit、Job 提交、worker 恢复、Review gate 工作流、候选入资产。Service 不能被不同 Router 复制实现；避免 Router 彼此 import，公共逻辑放 `services.py` 或独立 service 模块。

### 4.3 Repository

唯一包含 SQL 的层。每个 repository 负责一组实体，复用连接/事务和参数化查询；不得将查询散到 routers/views。项目列表统计应使用聚合查询，避免 N+1 请求/查询。所有写操作需要遵循已有 `touch` 等单一时间更新逻辑。

### 4.4 数据库

- SQLite WAL。
- 5 秒 busy timeout（已有设计）。
- 开外键约束；所有连接初始化必须保持 `PRAGMA foreign_keys=ON`（需以当前代码为准）。
- 每个 migration 一个明确事务；失败时完整回滚；迁移前备份有数据的数据库；保留最近 5 份备份（如当前实现已具备就回归测试，不重复造一个备份体系）。
- `schema_version` 记录已应用迁移；启动应用迁移需可重复执行、可安全跳过已应用版本。
- 路由层禁止 DDL/DML。

## 5. 身份、权限与项目访问

### 5.1 会话流程

1. 前端 boot 首次调用 `/api/auth/me`。
2. 401 时显示全屏登录闸门，不渲染业务模块。
3. 登录成功后，调用用户信息并继续同一 DOM boot，不做无意义整页跳转。
4. `must_change_password=true` 强制打开改密流程；服务端改密使该用户已有会话失效，前端用新凭证/新会话流程重新认证。
5. 用户菜单提供改密与登出；登出删除服务端会话后重载会话状态。
6. 会话过期是重新登录，不等于口令过期。系统不增加未在产品决策中确认的口令周期策略。

### 5.2 权限判定顺序

1. 找到有效会话和启用的用户，否则 401。
2. 检查业务权限点；缺失返回 403。
3. 对用户管理对象执行角色层级约束，越级目标不可见/写入按既有规则 404。
4. 对项目级对象调用统一 `access.ensure`：无项目访问资格返回 404；有可见权但操作级别不足返回 403。
5. 执行业务操作并在事务中更新关联记录。

禁止用 UI 控件可见性代替第 2–4 步；批量接口对每一 ID 重复执行相同判定。

### 5.3 权限点

当前 20 个权限点为基线。编码模型必须在真实仓库中读取它们的 `code/name/group` 与三角色映射，将其写入实现清单；不能通过名称猜测其完整列表。系统设置页面负责编辑映射，已有 admin 角色列保持禁用；超级用户通过 `is_superuser` 独立绕过权限判定，不依赖角色权限集合。

## 6. 文档/资产文件层设计

### 6.1 文档

- 正文文件在现有 workspace 根路径内；数据库只保存逻辑文档元数据、相对路径、文档类型、所属项目/集、状态、当前 Git commit 或文件哈希（字段缺失时按迁移添加）。
- 所有路径先规范化，校验目标文件真实路径仍位于允许根目录内；不能直接拼接用户传入的绝对路径。
- 写文件先写临时文件并 fsync/原子 rename（平台/文件系统允许时），成功后 git add/commit；若 Git commit 失败，需要保留临时结果或回滚文件到原版本并提示用户，不能静默显示定稿。
- 保存前检查 `expected_version`（Git commit/hash/updated_at）；不匹配返回 409，要求用户比较差异。
- 编辑锁有 holder、acquired_at、expires_at；采用心跳/续租或在保存时延长。锁已过期允许回收；过期与删除项目时清理锁。

### 6.2 资产图片/产物

- 资产参考图存储于数据文件目录，逻辑路径/表记录是授权依据。
- 生成产物、日志与临时文件分目录，推荐：`data/files/<asset_id>/...`、`data/jobs/<job_id>/outputs/...`、`data/jobs/<job_id>/logs/...`，如已有目录规范则保持现有路径并记录映射。
- 静态资源路由必须只服务允许目录；下载操作先按 Job/资产的项目访问规则鉴权。
- 删除操作先验证文件路径属于登记对象，不对客户端传入的 path 直接执行任意 `unlink`。
- 备份至少包括数据库、参考图/生成产物（按配置明确是否全部纳入）、文档 workspace 与 Git 仓库；数据库备份要使用 SQLite backup API 或一致性快照，不能只 copy 活跃的 `.db` 文件而忽略 WAL。

## 7. Job/队列/worker 设计

### 7.1 对象区分

- `Task`：可供用户跟踪的业务工作项，可代表生成、审核、人工待办或抽取；与某一业务对象关联。
- `Job`：实际执行单元/队列记录，保存一次具体模型/校验器调用、输入快照、输出、日志和成本。一个 Task 可以关联一个或多个 Job（如重试创建新 Job，原 Job 保留）。
- 队列只由 Job 表驱动；Task 状态从相关 Job/Review 的状态派生或通过 Service 协调，不允许出现第二个物理队列。

### 7.2 提交协议

`POST /api/jobs` 或等价当前端点只校验并登记任务，创建 Job ID 后快速返回（建议 202）。必须原子保存 Job + 参数快照 + 队列顺序/提交时间；触发 worker 失败时 Job 不得丢失。

建议请求字段：

```json
{
  "project_id": 1,
  "episode_id": 2,
  "shot_id": 12,
  "capability": "video",
  "kind": "video_local",
  "execution_mode": "local",
  "provider_code": "fastmetal",
  "model_code": "fastmetal-5b-qad",
  "prompt": "...",
  "params": {"width": 1280, "height": 704, "frames": 121, "steps": 3},
  "profile_id": null,
  "idempotency_key": "caller-generated-unique-key",
  "user_confirmed_cloud": false
}
```

上述为建议契约示例；字段名必须与现有 API 映射统一，不能未经兼容性评估随意改变已存在 endpoint schema。

### 7.3 Worker 生命周期

1. Dispatcher 原子领取 `queued` Job 并设置 `starting`，保证同一 Job 不会被两个 worker 同时领取。
2. 校验适配器、模型档、参数白名单、目标目录和权限快照；云端 Job 二次确认 `user_confirmed_cloud=true`。
3. 生成命令行参数列表，不拼 shell 字符串；调用 `subprocess` 时避免 `shell=True`，超时与取消有明确策略。
4. Worker 持续采集 stdout/stderr 到文件并做脱敏；若脚本有 `metrics-json`，解析耗时/峰值，不能假定所有 adapter 都有进度百分比。
5. 成功：校验输出文件存在且非空，将输出登记到 Job，保存 `succeeded`、结束时间、计量数据与成本；失败：保存退出码、错误分类、日志路径和可读摘要。
6. 取消：记录 `cancel_requested`，若能安全终止子进程则执行终止；否则显示“取消中”并在进程退出后归为 `cancelled`。取消后仍有云端费用的要照实记账。
7. 服务重启：在启动恢复流程中识别 `starting/running/cancel_requested` 但无活跃 PID/租约的任务；标记为失败/可重试或恢复租约，不能永远挂在 running。
8. 重试创建新的 Job 行并关联 `retry_of_job_id`，不得覆盖旧日志、旧成本或成功产物。

### 7.4 幂等/并发

- `idempotency_key` 在项目范围内唯一或全局唯一（二选一，建议全局唯一）；重复提交同一 key 返回已有 Job，不重复扣云端费用。
- 本地视频/图像/TTS/音乐工作使用一条串行本地 worker；同一模型的权重默认每 Job 加载/释放。
- 云端 API 可以并发，但需按供应商 rate limit 配置；DB 更新仍经 Repository/事务管理。
- SQLite 单写者特性需要短事务；禁止在持 DB 写事务时等待模型进程。

## 8. 模型适配器与路由

### 8.1 统一协议

每个 adapter 实现统一接口/协议，例如：

- `capabilities()`: 能力、模型列表、实际可用参数/运行时要求。
- `validate(params)`: 参数合法性与必要前置文件检查。
- `build_command(job)`: 构建可执行命令和环境配置，不泄露密钥。
- `run(job, cancel_token, log_sink)`: 在 worker 中执行 CLI/API 调用，返回规范化结果。
- `normalize_result(raw)`: 统一输出文件、时长、帧数、请求 ID、计量值、供应商计费摘要。
- `health_check()`: 检查脚本存在/版本、模型权重、密钥配置或远端 API 可用性。

如果当前代码已有不同 interface，应保留现有能工作的协议并实现兼容层，不需要为形式完全一致而重写所有脚本；关键是调用入口、结果格式和 Job 记录一致。

### 8.2 任务路由

| 能力/任务 | 默认执行路线 | 云端规则 |
|---|---|---|
| 文本 LLM（小说/剧本/润色/抽取） | 允许的国内供应商 API（设计稿建议火山方舟或 MiniMax，最终配置为准） | 没有合格的本地文本路线，provider 必须配置；成本与请求记录进入 Job |
| 图像（角色/场景参考图） | mflux + FLUX.1 系 | 只有用户明确选择并且已配置国内供应商时才允许云端路线 |
| 视频 T2V | FastMetal QAD 档 | 每镜头显式勾选云端；本地失败不自动转云端 |
| 视频 I2V/指定大模型档 | mlx-video（模型/权重已实测可用后才启用） | 每镜头显式勾选云端 |
| TTS | VoxCPM2 | 音频中心发起，生成中心执行 |
| 音乐 | ACE-Step 1.5 | 适配器/模型可用后启用；失败保留状态 |
| 自动校验 | 包装现有校验器脚本 | 不把校验器当作模型供应商；校验结果归 Review |
| 租卡/远程开源模型 | 仅在经济性评估证明更便宜且需确认许可后作为可选执行池 | 日常不默认使用；Windows/远程执行协议属于待定设计 |

### 8.3 云端选择界面

- 在镜头/Job 的提交确认步骤中展示“执行方式：本地/云端”，默认本地。
- 选择云端后强制选择供应商/模型档，并显示报价来源、计价单位、输入/输出计量预计值（无法预估就说明“以供应商实际账单为准”）。
- 需要用户主动勾选“确认此镜头使用云端并按供应商计费”。
- 不自动路由、不静默 fallback；失败重试也继承原执行方式，除非用户重新选择。
- 仅国内厂商；不把境外聚合 API、Veo/Gemini 等放进可选目录。候选供应商/模型名与价格是易变配置，正式配置前复核官方文档、许可和计价。

### 8.4 H3/LTX/音画同生许可与标识

设计稿记录 FastH3/MiniMax H3 的特定许可义务。启用相关模型之前，必须在项目许可证清单中核对**当前实际使用的模型权重/版本**和对应许可文本；不能把一个发行版的许可推断适用于所有版本。若该版本仍要求界面标明“MiniMax H3”，则 Job/生成中心界面要显著标记；满足特定营收门槛或内容分发范围发生变化时必须重新审查并按规则停用/另行授权。不能仅凭“内容一律不出海”就忽略其它许可义务。

音画同步方案须明确区分：
- 生成模型原生音轨；
- VoxCPM2 生成的最终对白音轨；
- Rhubarb/viseme 口型辅助数据。

三者不是天然同一时间线。对白镜头默认本地 TTS + 口型流程；原生音画同生优先作为可选路线，经听测/口型测试合格后才开放正式工作流。

## 9. 成本账设计

- Cost 是 Job 的计量快照，不另造一个可人工编辑的“成本真相表”。如需汇总快照，只能是可重建派生数据。
- 字段至少包括 `quantity`、`unit`、`unit_price`、`amount`、`currency`、`price_source`/`pricing_snapshot`、`billable_status`。
- 成本计算使用 Decimal 或整数最小货币单位，避免浮点积累误差；数据库字段类型结合当前 SQLite schema 选择整数微单位/文本 Decimal 表达，不能用无精度保证的浮点数作为金额真相源。
- 本地任务仍记录 elapsed time、内存峰值等资源指标；金额可为 0。
- 供应商计价单位不同（秒、视频时长、生成次数、Token 等），Job 必须保留原始 quantity/unit，不得把“数量”都硬转成秒。
- 项目级成本汇总按币种分别聚合；无汇率快照不做跨币种换算。
- 重试 Job 单独挂账；如果供应商计费但本地未收到结果，使用“待核对”状态，不能归零。

## 10. 审核与校验架构

### 10.1 流程

`Doc/Job` → 自动校验 Job 或 gate 执行 → 标准化 `Review` 记录 → 审核中心人工检查（如需要）→ 通过/驳回/退回 → 各模块只读显示。

### 10.2 Review 模型

Review 记录需要目标类型、目标 ID、目标版本/Job ID、gate 类型、结果、报告 JSON/文件、消息、创建/完成时间。人工签字需要签字人和签字时间。建议 `reviewer_user_id` 作为 Review 领域对象的明确身份引用；如果当前实现严格禁止 Review 引用 AppUser，则必须在实施前提出并解决“可审计签字”的设计冲突，不得用自由输入的签字名冒充已认证账号。

### 10.3 版本绑定

- 文档 Review 绑定 `git_commit` 或稳定的文件哈希。
- Job Review 绑定确切 `job_id`。
- 镜头 Review 绑定镜头当前内容版本/快照（以现有 schema 可行方式实现）。
- 被审核对象发生变化后，旧 Review 不能自动表示新版本通过；界面显示“版本已变更/需重新校验”。

### 11.2 建议补齐的端点簇

| 功能 | 建议接口 | 说明 |

| 校验 gate | `POST /api/reviews/gates` 或由 job 完成事件创建 | 包装现有校验器；不能再建第二队列 |
| Knowledge | `GET/POST /api/knowledge`、`GET/PUT/DELETE /api/knowledge/{id}` | 项目级/全局级权限检查 |
| 文本抽取 | `POST /api/extractions`、`GET /api/extractions/{id}`、`POST /api/extraction-items/{id}/accept` | 抽取本身为 Job；候选保留原文证据 |
| 项目统计 | `GET /api/projects/{id}/dashboard` | 汇总集、镜头、Job、Review、成本；不直接修改业务对象 |

### 11.3 API 共通规则

- JSON 请求/响应使用 Pydantic schema；不要返回 ORM/SQLite row 原对象。
- 创建成功使用 201；异步 Job 创建建议 202；无内容成功可用 204；具体状态按现有 API 兼容。
- 400：确认词/请求语义不正确；401：未认证；403：有可见对象但权限不足；404：资源不存在或不可见；409：重名/版本/并发冲突；413：上传超限；415：文件类型不支持；422：字段校验失败；429：供应商/任务限流；500 仅作未预期异常且日志要有 request ID。
- 错误响应规范化：`{"detail":"...","code":"...","field_errors":{...},"request_id":"..."}`；如果现有响应体只有 `detail`，前端保留兼容并逐步收敛。
- 请求需明确关联对象 ID，不接受用户传入任意文件绝对路径或 shell command。
- API 必须实现服务端的项目权限；批量响应结构明确 `done`、`skipped` 列表与总数。
- 高风险写入在后端重新验证 current user、项目权限、对象状态和确认字段。

## 12. 推荐数据流

### 12.1 Job 提交到执行

```text
View submits request
  -> API validates schema + global permission + project membership
  -> Service resolves provider/model/params and confirms cloud consent
  -> Repository transaction inserts Task/Job + cost snapshot + parameters
  -> Dispatcher sees queued Job
  -> Worker subprocess runs adapter/CLI/API
  -> Service normalizes result; Repository persists status/log/output/cost
  -> UI reads /api/jobs and project dashboard
```

### 12.2 文档改写

```text
Read current file + Git commit/hash
  -> create text Job with immutable input snapshot
  -> CLI/API generates staged output file
  -> user compares diff and explicitly applies
  -> atomic file replace + Git commit
  -> document metadata/status update
  -> validator job/gate
  -> Review entry
```

### 12.2.1 提示词生成与模板流程

提示词生成属于创作中心的创作操作；若需要调用 LLM，实际执行仍创建生成中心的 `text` Job。此流程不得建立第二个任务队列，也不得在没有用户确认时覆盖分镜字段。

1. 读取当前镜头或用户明确选择的文本范围，并冻结输入快照：镜头描述、台词/动作、已引用资产 ID、资产的一致性提示词、引用的 Knowledge 条目版本/内容摘要、目标能力（image/video）、目标模型/适配器、目标画幅/分辨率/时长（仅模型支持时）、用户提供的“必须保留/禁止改变”约束。
2. 从服务器端模型能力清单解析该模型实际支持的参数、负面提示词能力、分段/运动描述能力；不支持的字段不显示或不可提交。客户端不能自行声明模型能力。
3. 可选读取一个启用的 `prompt_template`。模板变量须以 schema 白名单替换；缺失变量、未知变量、无法解析的变量都要以字段级错误提示，不得执行模板中的命令或表达式。
4. 创建文本 Job 并记录 `input_refs_json`、模板 ID/版本快照、模型/参数快照以及输入/输出提示词快照；计费走 Job 唯一成本账。模板后续改动不能改变历史 Job。
5. 生成结果展示在独立预览区，至少包含主提示词、负面提示词（如适用）、分段/运镜提示（如适用）、引用资产和模型适配提示。用户可编辑/复制/重新生成。
6. 只有用户按“应用到镜头/提交生成”后，服务端才写入 `Shot.image_prompt` / `Shot.video_prompt` 或创建实际图像/视频 Job。写入时必须重新检查项目权限、镜头归属和所引用资产访问权。
7. 应用提示词到镜头与创建真实媒体 Job 是两个明确动作；用户若选择“直接提交生成”，需要在确认前看见最终提示词、模型、参数和执行方式，云端任务还要单独显示供应商/价格/计量单位并得到显式确认。
8. 失败时保留失败 Job、错误摘要和输入快照；不得假装提示词生成成功，也不得把失败结果自动写入镜头。

建议模板逻辑字段：`id`、`project_id`（NULL 表示全局模板）、`name`、`capability`、`style_code`、`target_model_code`（可空）、`template_text`、`variables_schema_json`、`default_params_json`、`is_enabled`、`version`、`created_at`、`updated_at`。物理表名与是否需要数据库存储，必须先查现有模板文件和 schema：如果当前已有文件型模板并且满足检索/版本需求，优先复用，不要为了表结构把同一模板保存两份。

### 12.3 资产抽取

```text
select Doc version -> extraction Job -> extraction_run/items with source offsets
  -> user accepts candidates -> asset Repository writes Asset + file if any
  -> shot candidates export Markdown only (v1)
```

# AI 视频生产平台数据字典

- 数据字典性质：统一逻辑数据模型 + 建议字段与约束
- 规则：设计稿确认的既有 schema 是迁移基线；凡标注“待核实/建议新增”的内容，实施前必须检查现有 migrations、models 和 repositories。不得直接用本字典重建数据库或删改旧列。
- SQLite 默认；时间/金额/JSON 列的物理表示需兼容现有代码。本字典使用逻辑类型描述。

## 1. 数据建模总则

1. SQLite 只保存元数据、状态、关系、配置元信息、Job 参数快照与成本；小说/剧本/分镜正文和媒体文件在文件系统，文档历史由 Git 管理。
2. 九个核心业务实体：Project、Episode、Asset、Doc、Shot、Task、Job、Review、Knowledge。
3. 身份实体：AppUser、Role、Permission；关联实体：user_role、role_permission、project_member、project_tag、session。
4. 其他技术实体包括 ProviderConfig、GenerationProfile（建议）、ExtractionRun、ExtractionItem（设计稿修订记录明确有抽取草案）、AssetImage（若现有实现采用单独图片登记表；否则沿用现有资产字段/路径机制）。
5. 各模块唯一写入归属：Project/项目中心；Episode/Doc/Shot/创作中心；Asset/资产中心；Task/Job/成本/生成中心；Review/审核中心；Knowledge/设定中心；AppUser/Role/Permission/ProviderConfig/系统设置。
6. `project_id` 是项目级数据隔离的重要键。全局资产/Knowledge 可以用空 `project_id` 表示，但必须有明确的权限和引用规则；不能仅凭 `NULL` 就允许任何用户修改。
7. 业务主键优先沿用现有 INTEGER ID；不要未经兼容性评估将现有 ID 改成 UUID。
8. 外键与级联策略必须逐表定义；文件系统副作用不由外键自动完成，需通过 Service 维护一致性。

## 2. 数据库实体关系概览

```text
AppUser ──< user_role >── Role ──< role_permission >── Permission
   │
   ├── owns Project (owner_id; ON DELETE RESTRICT)
   └──< project_member >── Project
                               ├──< Episode ──< Shot
                               ├──< Asset ──< AssetImage/files
                               ├──< Doc metadata ── filesystem + Git
                               ├──< Task ──< Job (one task may have retries/multiple jobs)
                               ├──< Review (target_type/target_id and version anchor)
                               └──< Knowledge

ProviderConfig ── supplies provider/model metadata to Job snapshots
GenerationProfile ── provides reusable params to create Job snapshots
Doc ──< ExtractionRun ──< ExtractionItem ── accepted Asset or exported Markdown
Shot ──< Job
Job/Doc/Shot ──< Review
```

关系图为逻辑关系。落库外键以当前真实 schema 及 SQLite 对多态目标的限制为准；`Review.target_type/target_id` 这类多态引用不能声明成一个普通外键，应通过 Service 校验存在性、项目归属和版本。

## 3. 字段类型约定

| 逻辑类型 | 表示与规则 |
|---|---|
| ID | SQLite INTEGER PRIMARY KEY，引用已有 ID 时使用实际列名 |
| TEXT | Unicode 文本；名称/代码应有长度上限；长正文不放入 DB |
| BOOLEAN | SQLite INTEGER，0/1；在 Python API 层映射 bool |
| DATETIME | 遵守现有数据库时间格式。已有字段不强行转换；新增表统一格式应在 CURRENT_SCHEMA 核验后确定。当前设计稿有本地时间语义，不得混算 last_opened_at 和 updated_at |
| JSON TEXT | 序列化 JSON；写入/读取需校验 schema。禁止用 pickle 保存外部可控数据 |
| RELATIVE_PATH | 相对于配置根目录的安全路径；不接受客户端绝对路径；服务端在使用前重新规范化验证 |
| ENUM/Literal | 应用层白名单校验，遵照已有设计不盲目在 SQLite 加 CHECK 约束（新增表是否可用 CHECK 需先评估迁移扩展性） |
| MONEY | 推荐整数最小货币单位或 Decimal 字符串，禁止以二进制浮点作为唯一金额真相源；保留币种和计量单位 |

## 4. 已确认/既有核心表

> 表/列的物理细节需以当前 `migrations/*.sql` 为准。以下主要是逻辑字段与约束；如实际列名有差异，应在代码映射中沿用实际列名并更新此文件，而不是无理由重命名。

### 4.1 `project` — 项目

| 字段 | 类型 | 必填 | 约束/说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键；保留既有 ID |
| `name` | TEXT | 是 | 去除首尾空格，不能为空；删除确认时用于精确匹配 |
| `description` | TEXT | 是 | 设计稿记录默认空串，上限 500 字 |
| `owner_id` | ID/FK | 是 | 所有人；`app_user.id`，删除账号时 `ON DELETE RESTRICT`；创建时取当前登录用户，后续仅通过所有权转移操作修改 |
| `status` | ENUM | 是 | `active`/`archived`；应用层 Literal 验证 |
| `created_at` | DATETIME | 是 | 创建时间；不因查看/归档改变 |
| `updated_at` | DATETIME | 是 | 最后内容修改时间；集/镜头/资产等内容变动时更新；打开项目、归档不能推动它 |
| `last_opened_at` | DATETIME/NULL | 否 | 最近打开时间；NULL 表示从未打开，不能作为内容修改时间 |
| `tags` | 逻辑关联 | 否 | 通过 `project_tag`/当前实现存储，最多 10 个标签、每个最长 20 字、去重；数组读取需有明确顺序或不承诺顺序 |
| `episodes_count` | 派生数值 | — | 不建议作为权威列，列表查询聚合计算 |
| `shots_count` | 派生数值 | — | 同上 |
| `assets_count` | 派生数值 | — | 同上 |
| `done_episodes_count` | 派生数值 | — | 基于 `episode.status='done'` 聚合 |

**索引建议：** `(status, last_opened_at DESC, id DESC)`；`owner_id`；项目列表所用的标签检索通过 `project_tag` 索引。若现有实现的排序表达式不同，保持输出行为相同。

### 4.2 `project_tag` — 项目标签

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `project_id` | ID/FK | 是 | 指向 project；随项目删除 |
| `tag` | TEXT | 是 | 归一化后的标签文本 |

**主键/唯一性：** 建议复合主键 `(project_id, tag)` 或唯一索引，防止同一项目重复标签。追加标签必须合并去重后截断/验证，不能误将批量追加实现成整组替换。全局 tag 读取需有稳定排序，不得依赖无 `ORDER BY` 的 SQLite 扫描顺序。

### 4.3 `project_member` — 项目协作人

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `project_id` | ID/FK | 是 | `project.id`，项目删除时 CASCADE |
| `user_id` | ID/FK | 是 | `app_user.id`，用户删除时 CASCADE |
| `added_by` | ID/FK/NULL | 建议 | 添加者；若现有 schema 已有该列则沿用；不作为通用业务审计系统 |
| `created_at` | DATETIME/可选 | 否 | 添加时间；如果当前没有则不为此单独破坏迁移 |

复合唯一约束 `(project_id, user_id)`；项目所有人本身不必重复存为协作人。只有管理员/所有人有权添加/移除协作人；协作人不能删除项目、管理成员或转移所有权。

### 4.4 `episode` — 集/创作单元

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `project_id` | ID/FK | 是 | 属于项目；项目删除时按现有级联逻辑处理 |
| `number`/现有序号列 | INTEGER | 是 | 集序号；以实际 schema 列名为准，在事务内分配以防并号 |
| `title`/现有名称列 | TEXT | 待核实 | 如果当前模型提供标题则沿用；不假设已有此列 |
| `status` | ENUM/TEXT | 是 | 必须支持 `done` 用于集级定稿计数；其它已有值从当前 Literal/校验中读取 |
| `created_at` | DATETIME | 是 | 创建时间，列名/默认值以迁移为准 |
| `updated_at` | DATETIME | 视 schema | 集自身内容修改的时间；是否实际存在待核实 |

**规则：** 集的创建/删除只属于创作中心；项目中心仅显示集数和已定稿计数。删除集前明确展示将删除/解除关联的镜头数，并按当前删除策略清理。

### 4.5 `asset` — 角色/场景/道具资产

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|

| `report_path` | RELATIVE_PATH/NULL | 否 | 较大报告文件路径 |
| `decision` | TEXT/NULL | 否 | 人工决策摘要 |
| `reviewer_user_id` | ID/FK/NULL | 人工签字时建议必填 | 明确签字人。设计稿中“业务表不引用账号”与签字可追溯之间存在冲突；这是 Review 领域的建议例外，实施前记录/确认；绝不能把自由文本姓名当作经过认证的身份 |
| `reviewed_at` | DATETIME/NULL | 否 | 人工审核时间 |
| `created_at` | DATETIME | 是 | 创建时间 |
| `updated_at` | DATETIME | 是 | 更新/决策时间 |

约束：签字 API 仅在审核中心实现；Review 必须绑定目标版本；自动校验与人工签字是不同 gate/阶段，不能用单一 bool 混合。

### 6.3 `knowledge` — 设定条目（九实体）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `project_id` | ID/FK/NULL | 否 | 项目内设定填项目 ID；全局设定为空；权限分开处理 |
| `title` | TEXT | 是 | 标题 |
| `category` | TEXT | 建议 | 角色背景/世界观/历史/术语等分类，不固定为不可扩展枚举 |
| `content` | TEXT/RELATIVE_PATH | 待核实 | 设计稿有条目正文；若正文较大可文件保存、DB 保存路径/摘要，不能误将小说剧本正文都搬入 DB |
| `summary` | TEXT/NULL | 否 | 用于列表摘要 |
| `evidence_refs_json`/关联表 | JSON TEXT 或关联表 | 待核实 | 证据快照引用；要能够指向资料文件及定位 |
| `tags_json`/关联表 | JSON TEXT 或关联表 | 否 | 可检索标签；沿用现有实现 |
| `status` | ENUM/TEXT | 建议 | 可用/归档，须先明确是否需要软删除 |
| `created_at` | DATETIME | 是 | 创建时间 |
| `updated_at` | DATETIME | 是 | 更新时间 |

若一个 Knowledge 有多条证据快照，建议独立的 `knowledge_evidence` 表；但如果现有设计以 JSON 路径列表实现，先沿用，不要创造第二种并行机制。

## 7. 抽取表（设计稿修订记录中已有草案）

### 7.1 `extraction_run`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `project_id` | ID/FK | 是 | 项目归属 |
| `doc_id` | ID/FK/或路径引用 | 是 | 被抽取文档及版本 |
| `doc_version` | TEXT | 是 | Git commit/hash，确定证据的原文版本 |
| `job_id` | ID/FK | 是 | 指向生成中心实际执行 Job，守住成本唯一账 |
| `extractor_model` | TEXT | 是 | 模型快照 |
| `status` | ENUM | 是 | 排队/运行/完成/失败/已复核等，映射现有草案状态机 |
| `idempotency_key` | TEXT | 是 | 相同文档版本和参数不重复创建入库副作用 |
| `created_at` | DATETIME | 是 | 创建时间 |
| `finished_at` | DATETIME/NULL | 否 | 结束时间 |

### 7.2 `extraction_item`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | ID | 是 | 主键 |
| `run_id` | ID/FK | 是 | 对应 extraction_run |
| `item_type` | ENUM | 是 | v1 允许 `character`/`scene`/`prop`；镜头候选仅导出 Markdown |

| `suggested_description` | TEXT | 否 | 候选描述/一致性提示词建议 |
| `source_start` | INTEGER | 是 | 原文偏移起始（明确按字符或字节，需要统一且固定） |

约束：证据偏移必须落在被冻结的文档版本范围内；接受候选时事务内检查幂等与资产唯一性。

## 8. 图片、媒体与可选表

### 8.1 AssetImage

当前设计明确图片落盘于 `data/files/<asset_id>/<uuid>.<ext>`，但物理图片登记是独立表还是资产列中的 JSON/路径列表需要检查现有 schema。优先沿用当前实现。若需要独立表，字段建议：`id`、`asset_id`、`relative_path`、`mime_type`、`size_bytes`、`width`、`height`、`created_at`。要求 `relative_path` 唯一、`asset_id` 外键，删除服务只删除数据库登记的文件。

### 8.2 AudioItem（可选）

| `review.status` | 推荐 `pending`, `passed`, `rejected`, `changes_requested`, `blocked` | 推荐规范，需与现有 validator 输出映射 |

任何 enum 增改必须同步更新：Pydantic 类型、前端筛选选项、数据库旧数据兼容、API 契约和测试夹具。不能只改一处。

## 10. 索引与完整性要求

建议（需对照 EXPLAIN QUERY PLAN 与现有索引后再添加）：

- `project(status, last_opened_at DESC, id DESC)`；`project(owner_id)`。
- `project_tag(project_id, tag)` 唯一索引；`project_tag(tag, project_id)` 用于标签筛选。
- `project_member(project_id, user_id)` 唯一；`project_member(user_id, project_id)` 用于查询某用户加入的项目。
- `episode(project_id, number)` 唯一，集序号在事务中分配。
- `shot(episode_id, number)` 唯一，镜号在事务中分配。
- `asset(project_id, type, name)` 或等价的归属范围唯一性实现。
- `job(status, queued_at)`、`job(project_id, queued_at DESC)`、`job(shot_id)`、`job(task_id)`、`job(idempotency_key)`。
- `review(project_id, status, created_at DESC)`、`review(target_type, target_id)`。
- `knowledge(project_id, category)`，需要搜索时可后续评估 SQLite FTS，但首版不额外引入复杂全文检索。

必须通过迁移/服务维护的完整性：

- 删除用户不能留下空的项目 owner。
- 删除项目清理已登记资产图片与关联行；不能删除未知文件。
- Shot 引用 Asset 的 ID 要在写入时验证同一用户可访问，删除 Asset 前检查引用。
- Review 的 target 与 version 由 Service 校验存在性/归属。
- `last_opened_at` 更新不能触发 `updated_at` 变更。
- 跨表派生计数尽可能查询聚合，不把派生值当权威持久列。

## 11. 必须从现有仓库核对的内容

下列项目不能由 AI 根据本文件臆造，必须检查真实代码：

1. 每个既有表的实际名字、列名、NULL/default/foreign key/index。

5. `episode.status` 的允许值、`shot` 当前列、`asset_ids` 的存储形式。
6. `provider_config` 真实十行结构、默认选择规则、环境变量命名。
7. 当前是否已存在 document/job/task/review/knowledge/extraction 表；禁止重复创建语义相同的表。
8. SQLite 时间格式、外键启用方式、迁移事务/备份机制。
9. 现有真实测试覆盖；不能只按设计稿的修订记录声称测试已经通过。

## 12. 数据字典变更流程

新增字段/表必须同时提交：

- migration SQL；

- 优先级：P0；依赖：W01/W02。

- 优先级：P0；依赖：W01。

### W07 — Job/Task schema 与统一队列

- 优先级：P1；依赖：W01/W06。
- 盘点当前 `job/task` 是否已存在。不存在时新增迁移，不重复建语义同等表；定义 Task/Job 职责与状态映射。
- 实现持久 Job 队列、幂等键、参数/提示词快照、单本地 worker 独立进程、日志路径、重启恢复、取消/重试状态。
- API 创建 Job 必须快速返回 ID，生成执行不在 API 请求内。
- 验收：同一 idempotency key 不重复执行；一个本地任务运行时不会并发启动第二个；杀掉 worker 后任务不会永远挂在 running；重试新建 Job 且原记录保留。

### W08 — 生成中心 UI 与成本账

- 优先级：P1；依赖：W07。
- 队列表/过滤/详情抽屉/日志/产物/失败原因/重试/取消/参数模板；成本列表作为 Job 聚合；项目中心只读摘要。
- Job 存单位、数量、单价、金额、币种、定价快照、账单核对状态；用 Decimal/整数最小单位避免金额浮点误差。
- 验收：云端任务的预计成本需用户确认；失败不默认归零；多币种分别汇总；重试保留原成本；本地任务记录耗时和资源数据。

### W09 — 本地 adapter 端到端

- 优先级：P1；依赖：W07/W08。
- 按真实仓库与模型权重完成：FastMetal T2V、mlx-video I2V（符合实际支持能力的模型档）、mflux image。
- 适配器只起 CLI 子进程，返回规范化 Job 结果；所有命令参数使用数组调用，不走 `shell=True` 拼接字符串。
- 验收：从浏览器分镜选择 → Job 入队 → worker 执行 → 产物登记/可预览 → 成本/耗时记录的完整回路；至少一个可复现的成功基准。

### W10 — 国内云端 adapter 与显式授权

- 优先级：P1；依赖：W06/W07/W08。
- 接入经许可证、国内可用性、官方 API、价格和密钥方案核验的文本/视频 provider；使用配置的国内服务，不新增境外聚合。
- 单镜头选择 cloud 后显示 provider/model/计价单位/预计成本 + 明确确认；重试继承 original execution mode。
- 验收：默认本地任务不会触发云端调用；模拟本地失败也不会自动云端兜底；云端错误/请求 ID/实际用量有日志并脱敏。

### W11 — 文档创作与 AI 操作

- 优先级：P1；依赖：W05/W06/W07。
- 实现/封版小说/剧本/分镜文档树，AI 起草/扩写/续写/润色/剧本化/提示词等操作；所有实际模型调用用 Job。
- 默认 diff 预览 + 用户确认应用；写回后 Git commit；版本状态不能早于实际写文件成功。
- 验收：端到端执行“润色 → 比较 diff → 应用 → Git commit → 校验报告”；失败过程保留原文。

### W12 — 分镜表与资产引用

- 优先级：P1；依赖：W03/W04/W05/W11。
- 完整表格字段以当前 schema 映射为准；实现镜头编辑、资产 picker/chips、每镜头作业提交与状态只读展示。
- 不做节点画布。确认 shot 属于 episode 还是 doc 的关系后保持旧 API 向后兼容。
- 验收：引用资产只读、跳转资产中心；多个 Job 可对应一个镜头；修改 Shot 后不会改变已提交 Job 的输入快照。

### W13 — 文本抽取候选

- 优先级：P1；依赖：W05/W07/W11/W04。
- 依据已存在 `接口草案-抽取.md`（若在仓库中）核对现有 `extraction_run`、`extraction_item`、幂等规则和六个接口；没有时按草案增量实现。
- 候选必须绑定 Doc 版本与原文偏移，角色/场景/道具经过人工接受后才入 Asset；镜头候选只导出 Markdown。
- 验收：重复提交不产生重复资产；原文证据偏移与被冻结版本一致；抽取成本通过 Job 入账。

### W14 — 审核中心与校验器 gate

- 验收：没有 reviewer 权限不能签字；文档版本变化后旧审核不能显示为新版本已通过；每句签字有稳定锚点。
