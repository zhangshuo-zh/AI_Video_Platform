## 1. 黄金样例

### 1.1 样例包

每次发布后按这一套东西原样跑一遍，跑通了才算发布完成。内容是原创的微型故事，只有三镜，本地预览档几分钟内能跑完。

**剧本**（创作中心 → 文档，约 300 字，保存后记录 Git 版本号）：

> 《修伞匠》
> 雨下了三天。巷口的老人还坐在他的摊子后头，面前摆着三把断伞。
> 镜一：雨巷全景。青石板反着光，修伞摊缩在屋檐下，老人戴着老花镜低头理伞骨。
> 镜二：手部特写。粗糙的手指捏着细伞骨，铁丝在指间绕了两圈，收紧。
> 镜三：中景。少女把一把修好的伞递回来，老人接伞，抬头笑了一下。雨还在下。

**资产**（资产中心，2 项）：

| 资产 | 类型 | 说明 |
| --- | --- | --- |
| 修伞老人 | 角色 | 参考图 1 张；一致性提示词：蓝布围裙、老花镜、灰白短发 |
| 雨巷 | 场景 | 参考图 1 张；一致性提示词：江南小巷、青石板、屋檐滴水 |

**镜头表**（创作中心 → 分镜，3 条，都关联上面两个资产）：

| 镜号 | 景别 | 生成档 | 提示词要点 |
| --- | --- | --- | --- |
| 1 | 全景 | 本地预览（FastMetal 1.3B） | 雨巷、修伞摊、屋檐，参考图＝雨巷 |
| 2 | 特写 | 本地预览（FastMetal 1.3B） | 手部、伞骨、铁丝，参考图＝修伞老人 |
| 3 | 中景 | 本地预览（FastMetal 1.3B） | 递伞、接伞、笑，参考图＝修伞老人＋雨巷 |

### 1.2 八步执行手册

1. **建项目与剧本**：项目中心新建项目 → 创作中心建文档《修伞匠·剧本》，粘贴 1.1 的剧本并保存。记录文档版本（Git commit 号）。界面见《系统使用说明书》§4 与 §6.2。
2. **抽取**：创作页对该文档发起文本抽取 → 抽出候选后逐条看原文证据，人工确认。当前版本不会自动把抽取结果变成正式分镜，确认后仍要手工建镜头。界面见 §6.4。
3. **建资产与镜头**：资产中心建 2 项资产并传参考图 → 创作中心建 3 条镜头，关联资产。逐条检查提示词和参考图是否对得上。界面见 §5 与 §6.5。
4. **提交生成**：生成中心选本地预览档提交。提交前确认路由、参数快照、费用提示；本地不花钱，云端档必须逐次勾计费确认。界面见 §7。
5. **查产物**：作业抽屉看产物文件、大小、时长、分辨率与 sha256；确认产物挂在对的镜头上。看不过眼的进「验证记录」登记产物验收结论。界面见 §7 与 §3.1（五档出处与验收结论）。
6. **音频**：配音/音乐三个运行时（VoxCPM2、ACE-Step、口型对齐）装好之前，界面显示未验证就是未验证，不在样例里假装跑过。装好后这一步补真实调用。界面见 §9。
7. **审核与导出**：审核中心过 gate 报告 → 人工签字 → 项目看板导出镜头清单。界面见 §8 与 §11。
8. **备份恢复**：按 §2.3 的三条命令做一次备份 → 校验 → 恢复到临时目录，确认项目、文档 Git 历史、Job 和产物引用都还在。界面与命令见 §16。

### 1.3 验收标准

每个结果都要能一路追溯到：输入文档版本 → 镜头 → 资产 → 模型档 → 参数快照 → Job → 费用 → 审核结论。任何一步失败，要能说出失败发生在哪一步。八步全部留下记录，这套记录就是这次发布可以复现的证据。

## 2. 故障演练记录

### 2.1 演练方式与证据分级

演练脚本有两个，都是一条命令重放全部条目，只打临时库、不打真供应商、不花一分钱：`tools/fault_drill.py` 是七条 Job 与队列演练（§2.2），`tools/pipeline_fault_drill.py` 是十条产线编排演练（§2.6）。

```bash
app/backend/.venv/bin/python tools/fault_drill.py
app/backend/.venv/bin/python tools/pipeline_fault_drill.py
```

证据分三档，本表只用这三档说话：**实测**＝本日在真实代码路径上跑出来的输出；**测试证据**＝pytest 里钉住同一语义的用例；**人工步骤**＝要花钱、要真机或要真账单，平台不代跑、也不许伪造。

### 2.2 七条演练结果（实测 2026-11-02）

| # | 演练 | 结论 | 观测 |
| --- | --- | --- | --- |
| 1 | 本地任务运行中 worker 被强制终止，重启后租约恢复 | 通过 | 租约未过期时 `recover_stale` 返回全 0，不误伤；租约过期后收成 `failed(worker_lost)`，可重试 |
| 2 | 云端已取得请求 ID、本地租约过期 | 通过 | 收成 `needs_attention` 而不是 failed；成本快照与 `pending_reconciliation` 原样保留，系统不会替人再打一次供应商 |
| 3 | 云端结果未知、账单未确认 | 通过 | 不给实际金额的核对被拒（409「确认结果前必须填实际金额」）；核对成功后 `actual_cost_micros=12345` 入账、预估 `cost_micros=16000` 不被改写 |
| 4 | 产物路径存在但文件为空/损坏 | 通过 | 空文件被拒「产物是空的：empty.mp4」；乱字节被拒「不是可识别的 video 文件」；正常 ISO-BMFF 头放行 |
| 5 | 重试前看预览、重试不覆盖历史 | 通过 | 预览返回链上合计 16000 微元、1 笔待核对、`may_charge_again=True` 及警告文案；重试落成新行（`retry_of=#4`），原行状态、错误、成本、产物路径一个字段没动 |
| 6 | 重复点击提交 | 通过 | 同一幂等键第二次回 200、作业号不变，库里该键只有 1 行 |
| 7 | worker 离线、队列积压、待核对告警 | 通过 | 心跳拨老后 `online=False、queued=4`，告警 `worker_offline`（含启动命令提示）；报警后排队的作业仍是 queued，没有被悄悄重试或判失败 |

同一语义在 pytest 里有常驻回归：`tests/test_attention.py`（18 项，含 `needs_attention` 告警码）、`tests/test_jobs.py`（队列语义与恢复）。

### 2.3 备份恢复演练（实测 2026-11-02）

```bash
cd app/backend
.venv/bin/python -m backup create /tmp/fv-restore-drill/bk     # 备份（对源只读）
.venv/bin/python -m backup verify  /tmp/fv-restore-drill/bk    # 校验
FASTVIDEO_DB=<临时目录>/platform.db FASTVIDEO_FILES=… FASTVIDEO_JOBS=… \
  FASTVIDEO_WORKSPACE=… .venv/bin/python -m backup restore /tmp/fv-restore-drill/bk --yes
```

观测：备份含库＋workspace 219 个文件＋jobs 33 个文件；校验报告 `schema 21，integrity ok，外键 ok`；恢复进临时目录后 `schema=21、表=26（含 schema_version）、job=13、model_validation=6`，与源库逐项一致（表数按 `sqlite_master` 现数，现役库与新库跑完迁移同为 26 张），恢复前的旧数据自动另存为 safety 目录。正式环境恢复仍必须对着真库做一次（人工步骤），演练不代替它。

### 2.4 两个状态不是一回事

`job.status=needs_attention` 说的是**作业**需要人处理；`billable_status=pending_reconciliation` 说的是**费用**待核对。云端作业可以同时占这两个标记，也可以只占后者（比如回执成功但账单没核对）。演练 2、3 的输出把这条界线跑实了：挂待核对时费用快照不动，核对时实际金额单独入账。

现库事实（2026-11-02 只读盘点）：job 共 13 条（succeeded 11、failed 2）；其中 #37、#38、#39 三条云端文本作业 `succeeded` 且 `pending_reconciliation`——这正是评审说的"预估金额不能当实际费用"的活样本，要等人在 DeepSeek 后台对出真实账单后走核对，平台不自动消掉它们。

### 2.5 人工步骤（阻塞项，平台不代跑）

| 事项 | 为什么必须人工 | 解除条件 |
| --- | --- | --- |
| 云端视频真调用演练 | 花钱，每次调用要操作者确认预算与费用上限 | 确认阿里云 Wan 档位后跑一条，登记 real_call |
| 三笔云端文本账单核对（#37–#39） | 实际金额只存在于供应商后台，平台不猜 | DeepSeek 控制台对账 → 生成中心核对 → 登记 real_call |
| 音频三运行时真调用 | 运行时未装齐，装了才算 | VoxCPM2/ACE-Step/口型对齐装好并健康检查通过 |
| M5 Ultra 目标机基准 | 目标机未到货，查无记录就显示 UNKNOWN，不填推算值 | 机器到货后跑 §1.2 八步＋目标机档验证 |
| 正式库上的完整恢复 | 演练恢复进的是临时目录，正式恢复会覆盖 data/ | 定维护窗口，备份→verify→restore --yes→重启验证 |
| 产线生成节点用真实模型跑通一镜 | 本机没有图像／视频运行时，且真调用要花钱、要人确认预算 | 运行时装好或云端档位确认后，用「视频生产」模板跑一条 run，再去审核中心产物页签签字 |

### 2.6 产线十条故障演练（阶段 B，实测 2026-11-03）

脚本在 `tools/pipeline_fault_drill.py`，一条命令重放全部十条，同样是临时库＋mock 适配器，不碰真供应商、零付费：

```bash
app/backend/.venv/bin/python tools/pipeline_fault_drill.py
```

演练用的模板是四条节点的缩小版：读项目 → 关键帧（按镜头展开，2 镜）→ 产物检查（按镜头展开）→ 验收（等签字）。故意比内置的 13 节点模板短，好让每一条演练的观测都能一眼看完。

| # | 演练 | 结论 | 观测 |
| --- | --- | --- | --- |
| 1 | 建了运行、还没推进过就崩 | 通过 | 重启后从库里的状态接着走：7 个节点一个没多一个没少，`read_project=completed`，关键帧节点当轮派出作业 |
| 2 | 节点已就绪、作业还没提交就崩 | 通过 | 补提交且**只**提交一条：节点拿到 `job_id`，幂等键 `pl-<run>-keyframe#s<镜头>-a1`；连推两轮库里仍只有 1 条产线作业 |
| 3 | 作业已落库、节点还没关联就崩 | 通过 | 按幂等键认回原作业，节点重新指向它，产线作业仍是 1 条；事件流里如实记了 `reused=true` |
| 4 | 作业跑一半 worker 被强制终止 | 通过 | `recover_stale` 收成 `failed(worker_lost)`，节点跟着 `failed`，运行状态 `failed`；**作业数没变——产线不自动重试** |
| 5 | 作业已成功、节点还停在执行中 | 通过 | 按 Job 真相对齐：两格关键帧 `running → completed`，产物检查同轮做完，运行进 `waiting_review` |
| 6 | 一镜失败，只重试那一镜 | 通过 | 新作业 `retry_of` 指向旧行、`attempt=2`，旧行原样留着；好那一镜的作业与 `retry_count=0` 一个字段没动；项目作业 2 → 3，其中产线幂等键仍 2 条 |
| 7 | 卡在等签字时重启 | 通过 | 连推三轮仍是 `waiting_review`，不派新活、不改审核状态；签字之后**同一轮**就收尾，运行 `completed`（4/4）并写 `finished_at` |
| 8 | 暂停时作业还在跑 | 通过 | 不强杀：暂停期间作业自己跑到 `succeeded`，节点照实收成 `completed`，下游只到 `ready` 不往下派，运行状态 `paused`；`resume` 那一轮就把产物检查做完 |
| 9 | 云端已取得请求 ID、本地租约过期 | 通过 | 收成 `needs_attention` 而不是 failed；请求 ID、预估 `cost_micros`、`pending_reconciliation` 三样原样保留，节点 `attention`，**产线不替人再打一次供应商** |
| 10 | 两个线程同时推进同一条运行 | 通过 | 两个线程各调一次 `advance_run`，2 格每格库里只有 1 条作业（幂等键唯一），节点行数 7 未变。挡住重复的是 `try_begin` 的行数——第二个调用拿到 0 就直接退出。这一条只报观测到的结果，不去猜哪个线程赢了 |

同一语义在 pytest 里有常驻回归：`tests/test_pipeline.py`（28 项）。

**这一节的证据边界**：十条全部走假适配器。按实施文档 §12.3 的口径，**Mock 只能证明代码路径和故障处理逻辑，不得作为真实模型生产验证证据**；`model_validation` 里一条记录都没因此新增，任何槽位的「生产可用」也不会因此亮起。真跑一镜要等上面 §2.5 那条人工步骤解除。

### 2.7 产线页面真浏览器验收（阶段 C，实测 2026-11-03）

无头 Chrome 起 live API 与 live worker，用临时管理员与临时只读账号走真实登录；临时项目、临时集、剧本与一条镜头在脚本里建，跑完级联删除。样例用的是 §1.1 的修伞匠微故事（三句正文＋一镜雨巷全景）。

| 节 | 验什么 | 观测 |
| --- | --- | --- |
| 0—1 | 准备与入口 | 临时项目建好、顶栏切过去；侧栏顺序 `generate → pipeline → audio`，产线中心在生成中心之后 |
| 2 | 模板页签 | 三份内置模板都在，写清只读、没有拖拽；标准模板展开 13 个节点 |
| 3 | 发起运行 | 弹窗模板下拉带版本与节点数；列表出现一条运行；**一次 `advance` 都不调**，live worker 的 `tick()` 把它推到 `waiting_review`；前五个内部检查完成，关键帧在等前置，详情画出 13 个节点 |
| 4 | 暂停／恢复 | 暂停后状态 `paused`；恢复后回到 `waiting_review` |
| 5 | 人工审核 | 在审核中心跑 gate 并整份签字 → `confirm_script` 自己完成；关键帧因本机没有运行时以「图像的本地档还没填 provider/模型」失败，运行 `failed` |
| 6 | 单格重试 | 失败行有重试按钮、要确认；节点记了重试次数；原因没除掉仍失败；时间线写着重试与失败 |
| 7 | 同集第二条 | 改一句正文，旧签字作废；上一条结束后允许再起一条；已有未结束运行的集在下拉里禁用；取消要确认；取消后等签字节点跟着取消 |
| 8 | 只读账号 | 能看运行与模板；推进／暂停／取消／重试四个动作都不显示；直接调发起接口 403 |
| 9 | 截图与窄屏 | 夜间／模板／白天三张截图；380px 横向溢出修前 **154px**、修后 **0px** |
| 10 | 清理 | 临时项目级联删运行、节点与事件（残留 0）；临时账号删掉；全程无未捕获 JS 错误 |

**这一轮撞出并修掉的三条收尾缺陷**（都在 pytest 里有回归）：① 失败运行的下游节点永远 `blocked`，`finished_at` 落不下来，同一集此后一直 409——收尾判据改成「全部终态**或剩余节点不可达**」；② 已结束的运行点重试不会重新打开——重试事务里 `reopen()` 清空 `finished_at`；③ 取消运行会留下仍在等人的 `human_gate`，迟到的签字能把它收成完成——取消时一并收掉。另按审计 R1 给 `jobs.cancelled()` 补了 `worker_id` 归属守卫。
