## 阶段一：诊断与设计

### 日志路径与错误回执

`app/backend/routers/jobs.py` 的 get_worker_process、start_worker_process、stop_worker_process、start_many_workers、stop_one_worker 均将 str(sup.WORKER_LOG) 直接序列化。worker_supervisor 的目录创建、日志打开失败及子进程退出回执还可能带原始异常和日志尾部。

不能复用 jobfiles.relative：它只接受 JOBS_DIR 内的产物路径，worker.log 不在该根目录，直接复用会抛 ValueError。采用稳定展示标签 data/logs/worker.log，内部真实 WORKER_LOG 不变。错误回执和日志尾部沿用统一密钥脱敏，再将已知目录换成标签、其他宿主绝对路径替换为本机路径标记；FV_KEY_VOLC 这类 KEY 位于中间的敏感环境变量也纳入脱敏。

### 验证历史筛选

`app/backend/repositories/validation.py:ValidationRepository.list_recent/count` 原来只有 limit 与 before_id，无 kind/state 条件。`routers/settings.py:list_validations` 因而只能返回未筛选页和全库数量。

设计：kind、state 使用既有 ValidationKind / ValidationState Literal，非法值回 422；only_bad 等价 state <> ok。仓储共用参数化 WHERE 构造，列表增加 id < before_id，计数不含游标边界。state=ok 与 only_bad=true 合取结果为 0 条。limit 仍最多 200，不引入 OFFSET，不修改默认数组和 X-Total-Count 契约。当前没有支持只按 kind/state 前缀的专用索引，COUNT 仍可能扫描历史；本轮没有未经负载证据新增索引。

### 进程、心跳、配置与审计

- worker_supervisor._pid_alive 原来将任意 OSError 当成死亡，EPERM 也可能造成残留误判；应仅把 ESRCH/ProcessLookupError 当作明确死亡，其他探测失败保守视为存活。
- current 只读 PID 文件；已有 clean_stale 方法没有对应显式接口，且删除失败也可能被计为已清理。GET 必须保留诊断痕迹；清理需要单独的受权限保护 POST，确认死亡并核对登记文件未被替换后才删除。
- /worker/process 原 count/pids/running 是受管进程事实，不能直接改成所有心跳的总数，否则会让旧客户端误以为外部 PID 可停止。补充本机在线心跳观测字段，仍以 job 仓储的 worker_node 为唯一心跳来源，不建第二套状态表。
- services/jobs_pkg/monitor.py:set_concurrency 原来会因局部请求而重置未传的全局／每类设置；且 isinstance(user, dict) 排除了真实请求的 sqlite3.Row 操作人。
- 并发配置虽然尝试 record(worker_limit, ...)，但 repositories/config_log.py 与 config_change_log 的双重白名单都只有 3 个选路 subject，实际留痕失败。需要扩展原表，而不是另建审计或运行状态表。
- worker_daemon.load_config 对 JSON 内错误 desired 类型抛异常；save_config 直接覆盖文件，读者可能看到半截 JSON；start_thread 的读判起没有互斥。

## 阶段二：最小补丁与契约

### 已修改的生产代码

1. `worker_supervisor.py:public_log_path/public_message`：日志展示标签和消息脱敏；所有 5 个进程响应通过 `routers/jobs.py:_process_out` 收口。日志尾部在截断前脱敏，避免截断敏感值后漏遮盖。
2. `repositories/validation.py:_history_filters/list_recent/count` 与 `routers/settings.py:list_validations`：增加 kind/state/only_bad，WHERE 绑定参数，数组及总数头保持兼容；非法游标非正数回 422。
3. `worker_supervisor.py:_pid_alive/clean_stale/stop`：权限探测保守处理；显式清理只返回真实删除的登记，常规探测放在启动锁外，删除前在锁内重新确认 PID 与文件身份；stop 一次取得列表快照，不重复探测同一组状态。
4. `POST /api/worker/process/clean-stale`：system:config 权限；不向任何进程发停止信号。清理权限不足时保留文件并返回 0 条实际清理数。
5. `services/jobs_pkg/monitor.py:process_observation` 与 `schemas/jobs.py:WorkerProcessOut`：新增 external_online_pids、external_online_count、heartbeat_online_count、total_observed_count。只取本机、未过期心跳，按 PID 去重；心跳表示观测，不保证进程此刻仍活着。原 count/pids/running 语义保持不变，外部 PID 仍不能经 stop_one 停止。
6. `services/jobs_pkg/monitor.py:set_concurrency/_set_concurrency`：同一 BEGIN IMMEDIATE 中读取并合并局部字段、评估、保存及写痕。未传字段保留；显式 global_max=null 回默认、per=null/{} 清除每类覆盖。评估只读有界 Job 样本与机器内存信息，不等待模型、网络或进程启动。正确记录 sqlite3.Row 操作人。
7. `schemas/jobs.py`：并发和启动 per 值限制 0—64，资源类白名单一致；global_max 与 count 沿用原上限。未将内部类型别名新增为公开模型门面契约。
8. `worker_daemon.py:load_config/save_config/start_thread/check/_record`：无效文件内容回关闭；同目录临时文件、fsync、os.replace 原子替换，失败清理临时文件并保留旧配置；线程启动在本 API 进程内互斥。对外守护错误及动作明细脱敏。
9. `routers/jobs.py:put_worker_daemon` 与 `repositories/config_log.py`：守护配置保存失败回安全 400；成功更新记操作人、开关和期望数量。审计不写路径、环境变量值或密钥。
10. `0057_worker_config_audit.sql`：在原配置审计表增加 worker_limit / worker_daemon subject，保留旧记录、自增高水位、操作人外键及两把索引，未增加业务表。现值仍归 worker_limit 与 daemon.json，Job 仍是唯一生成队列与执行事实。

### 使用示例与边界

- `GET /api/providers/validations?kind=real_call&state=failed&limit=50`：全历史中匹配的最新一页。
- `GET /api/providers/validations?only_bad=true&before_id=123`：所有非 ok 记录的更早一页；X-Total-Count 是当前 kind/state/only_bad 下全部匹配数，不只统计 id < 123。
- 无筛选时仍返回 list[ValidationOut]；未包装为 items 对象。
- `POST /api/worker/process/clean-stale`：管理员明确触发，GET 不自动清理。
- 工作区前端本轮保持原样：服务端参数及观测字段已可用，但不宣称现有前端页内筛选已自动改为服务端筛选。

## 可选 P1：最小方案，未新增生产接口

建议独立只读 `GET /api/jobs/model-statistics`，复用 `services/jobs_pkg/billing.py:job_cost_summary` 的可见项目规则及 `repositories/jobs_parts/cost.py` 的 BILLABLE_WHERE，不改变既有 CostSummaryOut。不得以全局监控为由绕过项目可见性。

- 成本按 capability、execution_mode、provider_code、model_code、currency 分组；每个 Job attempt 保留为独立记录。沿用既有预计成本口径，实际金额另列且 NULL 不能当 0；不得混合币种或用当前默认模型替代历史快照。
- since/date_from 选一个主参数及别名，冲突时拒绝；明确按提交 created_at 筛选。用 `created_at >= ? AND created_at < ?`，不对列套 date()，并统一输入与库中服务端本地时间的时区口径。
- 执行耗时只读 elapsed_ms 等必要数值与维度列，不拉 prompt、input_refs 或 resources 大文本。均值/P95 标注为 Job 执行耗时，不能冒称纯模型推理耗时。成功且耗时非空、非负的样本参与；缺失量和失败量另报，mock 不冒充真实模型样本，FFmpeg 单独归工具组。
- P95 可用 SQLite 窗口 row_number/count 取 nearest-rank ceil(0.95*n)；不引入第二套调度或统计状态表。
- 临时 20000 条 Job、窗口内 10000 条／5 组的单次可行性取样：成本聚合 8.429 ms，均值/P95 23.161 ms。均使用 idx_job_project_id；成本有 GROUP BY 临时 B-tree，P95 有排序与分组临时 B-tree。该结果不是现役接口压测或 SLA。
- 当前无 `(project_id,created_at)` 时间范围索引，窗口筛选仍扫描项目记录；若进入实现，应先量真实项目规模和写入成本，再决定是否新增索引。样本量、空值、重试、权限、币种及时间边界要配套测试。本轮不偷偷扩展为未经产品验收的统计 API。

取样脚本与计划：`.out/monitor-backend-20261117/statistics_probe.py`、statistics-plan.json；仅临时库，不访问供应商。
