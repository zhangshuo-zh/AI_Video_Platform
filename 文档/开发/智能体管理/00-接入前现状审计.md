## 1. 一句话结论

说明书 §6 列的八个逻辑组件里，**六个平台已经有了**，而且比说明书想得更细——配置、端点、健康、场景路由、云端计费授权、探测留痕各自都有唯一出处；真正缺的是**三样**〔代码可确认〕：

1. **一条会规划的执行回路**。今天平台里所有 AI 活儿都是"一次提示词 → 一条 Job → 一个产物"，没有多步、没有工具调用、没有"跑到一半回头改计划"。`cloud_run.py` 发的也是单轮 chat（`messages` 里就一条 user）。
2. **本地文本运行时**。`provider_config` 的文本·local 是一行空槽（provider 与 model 都是空串、enabled=0），`adapters.py` 的 text 族三条（deepseek／volc／minimax）**全部** `backend="cloud"`。也就是说"本地优先"这句话在今天这版代码里，文本这一类**没有任何一条腿**。
3. **"一次写操作"这一档审批**。现有签字审的是"一份内容能不能用"（`review_item` 的 document／job 两档），没有"这个动作允不允许发生、参数对不对"这一档。

所以本审计的结论不是"照说明书建一个智能体中心"，而是**两条分开**：配置面**全部复用**模型中心（说明书 §7 那两张配置表如果照建，就会长出第三份"这一档模型在哪"——那是本项目这两轮反复在修的同一类缺陷）；要新造的只有**运行记录**（run／step）与**白名单工具**这一条回路。〔代码可确认〕

## 4. 环境侧：本地智能体这条腿现在能不能落地

说明书 §3.1 举例的端点与模型是 `http://localhost:11434` ＋ Qwen3 30B A3B。本机实测：

| 项 | 实测 | 层 |
|---|---|---|
| `ollama` 可执行 | `/opt/homebrew/bin/ollama`，client version 0.35.1 | 〔目标机实测〕 |
| 服务在不在 | `ollama list` → `Error: could not connect to ollama server`；`lsof -nP -iTCP:11434 -sTCP:LISTEN` **零行** | 〔目标机实测〕 |
| 机器 | Apple M4，**16 GB RAM**，系统盘余 171 Gi | 〔目标机实测〕 |
| 平台文本能力配置 | `provider_config` 文本·local：provider 空、model 空、enabled=0；文本·cloud：deepseek／deepseek-flash，`key_env=DEEPSEEK_API_KEY`，is_default=1 | 〔现役库只读〕 |
| 已登记模型 | `model_registration` 三行：text·cloud·deepseek、video·cloud·wan、video·local·fastmetal。**text·local 零行** | 〔现役库只读〕 |
| 任务策略 | `model_policy` 九行全 `enabled=0`、`preference='any'`、槽位空——模型中心那一页立了骨架，还没人配 | 〔现役库只读〕 |
| 引擎实例 | `engine_instance` **0 行**（Draw Things 在监听 127.0.0.1:7860，但库里没登记） | 〔现役库只读〕＋〔目标机实测〕 |

推论两条，都影响排期：

1. **本地智能体在这台机器上现在跑不了说明书举例的那一档**。16 GB 统一内存装不下 30B-A3B（权重＋上下文），能跑的是 3B—8B 量化档；那一档能不能做"多步规划＋工具调用＋结构化输出"是**未验证**的，不能假设。〔目标机实测〕推论
2. **"本地不可用时提示用户、不静默切云端"这条原则，今天恰好是唯一可行的形态**——因为本地根本没有可用腿，任何"本地优先"都会当场落到"提示用户"那一支。这不是实现得好，是**还没实现**，别把它写成通过。〔代码可确认〕

## 5. 与现有各功能的联动点盘点

说明书 §9 阶段 4 说"从资产缺失盘点和候选生成开始接入业务模块"。今天这些位置长这样〔代码可确认〕：

| 页面 | 现有 AI 入口 | 走的形状 | 接 Agent 还差什么 |
|---|---|---|---|
| 创作中心 · 文档 | `GET/POST /api/documents/{id}/ai-options`、`ai-jobs`、`ai-jobs/{job}`、`.../apply` 四条；六种操作（起草／扩写／续写／润色／剧本化／提示词）落点在 `docai.py` 写死，落盘仍走 `services.save_content()`（原子写＋Git＋编辑锁） | **已经是"人选参数 → 模型出文 → 人签应用"**，Agent 化程度最高 | 差的只是"参数由谁给"：Agent 提议 → 人确认 → 同一条 apply |
| 资产中心 · 资产创作 | `asset_studio.py`＋统一 Job 提交（人物履历／形态／概念图） | 一次提交一条 Job | 需要"缺什么资产"这一步是 Agent 读出来、而不是人列出来 |
| 文本提取 | `routers/extraction.py`，提交即建 Job，结果进候选分诊页 | 一次提交＋候选 | 同上，候选的**取舍**仍可给 Agent 建议 |
| 分镜／镜头工作台 | `precheck.py` 三档清单（阻塞／警告／通过），四个入口读同一份 | 人点提交 | Agent 可产"骨架"，但提交与签字入口不变 |
| 审核中心 | `review_gate`（校验器）＋`review_item`（签字，**唯一写入口**）＋`review_check`（人工清单，改判覆盖） | 人签 | 审批档扩一档即第 6 节丙 |
| 生成中心／产线 | 唯一队列 `services.submit_job`；产线只读 Job 事实 | 队列 | Agent 发起的活儿**必须**仍进这一条队列，不开第二条 |

联动结论一句：**这些入口今天都要求人先填参数，Agent 联动的本质是"少一层人填参数、多一层人审批"，不是新加一批页面。**〔代码可确认〕

## 6. 三处和既有裁定撞上的地方（要人点的）

**甲｜路由到底算不算数。** 说明书 §3.3 要策略层真正决定走哪条轨；平台裁定 MC1（2026-11-04）＝ `model_policy` **不参与** `resolve_provider()`，默认轨唯一来源是 `provider_config.is_default`，`adapters.POLICY` 里 `no_auto_fallback=True` 与前端那句 `policy.no_auto_fallback` 必须说同一句话。
推荐：**不动全局默认轨**。Agent 的选路只发生在"Agent 代表人提交的那一条 Job"上——把场景与建议轨作为**提交参数**显式带上，仍过 `services.submit_job` 里 `user_confirmed_cloud` 那道闸门。这样说明书要的"按任务类型配置路由"是真的，MC1 也没被推翻（人没点的轨，平台一条都不会自己走）。

**乙｜要不要操作审计。** 说明书 §3.5 要配置变更审计与运行审计；设计稿 §8 明写"没有操作审计……要做就是新表＋每个写接口一次 INSERT，属于独立一轮，v0.87 明确不做"。
推荐：**只给 Agent 这条线立事件表**（Agent 是新增的写入口，它得自证干了什么），**不**扩到全业务表，配置变更审计仍不做（沿用"探测现算、`model_validation` 留痕"）。这样"审计"这个词在平台上第一次出现时，边界是清楚的，不会变成第 18 个模块都欠一次 INSERT。

**丙｜审批落在哪张表。** 说明书 §7 建议新表 `agent_approval`（动作／参数哈希／成本摘要／有效期）；不变量 3 说"签字只有审核中心一个写入口"。
推荐**甲案**：`review_item.target_kind` 加第三档 `agent_action`——与 D1 把 document 扩到 job 是同一做法，天然继承"别处只显示状态、不许别处签"。参数哈希进 `base_version`（就是被审对象的指纹，语义正好），成本摘要进 `note`。这样平台只有**一处**"人点头"的落库处；否则界面上会同时存在两个"待审批"，而它们互不知道对方在做什么。

## 7. 边界：新模块管什么、不管什么

撞过的坑先写在这，免得实现时再撞：说明书 §4 的页面里有"本地智能体／云端智能体／任务路由策略／运行与健康记录"四个 Tab，而模型中心已经有"模型仓库／引擎管理／调用策略／运行监控"四个二级页——**照抄就是同一份事实在两处可改**。

定这条界（与"一个实体只有一个东家模块能写"同一条纪律）：

- **模型中心**（已有，不动）：这一档能力有什么规格、在哪台机器的哪个路径/端点、什么价、健康如何。写入口 = `model_registration`／`engine_instance`／`model_policy`。
- **智能体中心**（新）：**谁替人做决定，以及决定到哪一步了**。装 Agent 身份（能用哪些白名单工具、服务哪些任务场景、审批与数据范围）、Run／Step／Event 记录、待审批动作。它对模型只做**引用＋跳转**，一个模型字段都不复制；健康读数从模型中心那三个现测函数取，不落库。
- 说明书 §3.2 的"密钥安全引用"与 §3.4 的"项目权限校验"**已经是平台纪律**，新模块只写"沿用"，不实现第二套：密钥只存变量名（`key_env`／`shared_secret_env`），项目归属过 `access.ensure()`，写操作过 `job:submit`／`asset:write`／`doc:write` 这些现有点。
- **不新增权限点**：沿用模型中心的做法（18 个权限点保持原样，`system:config` 管配置、`job:submit` 管发起、`review:sign` 管审批）。〔代码可确认〕0024 撤过两条，历史上"一个新权限点都没加"是产线那几轮共同的收口口径。

## 9. 开工门禁与阶段切法

对照说明书 §9 的六个阶段，本审计给出的切法**不是**它的顺序，因为说明书把"配置 CRUD"排在第一位，而那一半平台已经做完了——先做已完成的那一半是浪费。

| 阶段 | 内容 | 新表 | 新端点 | 门禁（现在能不能开） |
|---|---|---|---|---|
