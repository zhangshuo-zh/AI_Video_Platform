## 0. 一句话结论

现有平台的 Job / Worker / 成本 / 恢复 / 权限这一层**可以直接当产线的执行底座用**，不需要重构；真正缺的只有三件：**流程编排记录（3—4 张新表）**、**镜头级人工审核的写入口**、**一个常驻的推进节拍**。而当前架构有两条硬限制会让附件里的部分节点今天跑不起来：**Worker 全局只跑一条作业（并发为零）**、**图像与音频在本机没有可用运行时**。这两条必须在验收口径里写明，不能用 Mock 成功冒充。

附件最后点名的三个技术问题，答案分别在这里：

1. **节点与 Job 创建之间如何崩溃后不重复提交** → §2.2—§2.4（结论：`db.transaction()` ＋ 确定性幂等键 ＋ 原子转态，不需要 outbox 或消息中间件）
2. **Worker 如何在不破坏单机资源约束下逐步支持调度** → §1「Worker 并发」行 ＋ §8 R2（结论：今天并发为零，两处写死；阶段 B/C 不碰，阶段 E 才改，并发数必须由 M5 Ultra 真实基准决定）
3. **审核完成后如何可靠通知产线继续** → §3（结论：不要发明回调，调度器进 worker 循环 ＋ 一个幂等的 `advance`，两处共用同一函数）

## 2. 幂等、崩溃窗口与事务能力（附件 §6.3 的三个技术问题之一）

### 2.1 现成的幂等能力

- `job.idempotency_key` 全局 UNIQUE（`migrations/0015_job.sql:32`）。SQLite 把 NULL 当互不相等，所以不传键的行不受影响。
- `POST /api/jobs` 同键第二次来：返回 **200 ＋ 原行**，不重跑；键被别的项目占用时只回一句 409「这个幂等键已被占用」，不把那条作业的内容带出来（`routers/jobs.py:66-77`）。
- 重试是**新建一行**：`attempt=原行+1`、`retry_of_job_id` 指向原行、原行的 `superseded_by_job_id` 指向新行；原行的日志／耗时／成本／错误一个字段都不动（`repositories/jobs.py:345-386`）。附件 §6.4 要求的语义**已经实现**，产线直接沿用，不要另写一套。

### 2.2 现存的崩溃窗口（真实缺陷，产线会踩同一个坑）

`extraction_submit()` 里两步各开一个事务：先 `job_repo.create()`，再 `extraction_runs.create_run(job_id=…)`（`services.py:639-667`）。进程在两步之间死掉，就会留下**一条没有归属的付费 Job**——抽取页看不见它，成本账里却有它。文档 AI（`submit_doc_ai_job`）同样不传幂等键，靠"一次操作一条作业"的语义兜着。

这正好回答了附件 §6.3 的问题：**不需要 outbox、不需要消息中间件**。仓库里已经有 `db.transaction()`（`db.py:52-80`，`contextvars` 版，嵌套的 `get_conn()` 借用同一条连接、`BEGIN IMMEDIATE`、只在最外层提交），而 `submit_job()` 全程是**纯库内写 ＋ 纯计算**（读 `provider_config`、跑参数白名单、`job_repo.create`），不碰 Git、不碰磁盘、不发网络请求 ⇒ 完全符合 `transaction()` 的边界要求（事务里只做库内写）。

### 2.3 建议的产线提交协议（待裁项 D2）

```
with transaction():                      # 一个事务，要么全有要么全无
    1. 节点原子转态：UPDATE … SET status='submitting'
       WHERE id=? AND status='ready'      # rowcount!=1 就整段放弃＝重复触发被挡
    2. submit_job(...)                    # 带确定性幂等键 pl-<run>-<node>-<attempt>
    3. UPDATE 节点写 job_id、转 'running'
    4. INSERT pipeline_event('job_submitted')
```

三层保险，任何一层单独失效都不会重复提交：

1. **事务**保证"节点有 job_id"与"Job 存在"同时成立，杜绝"Job 已建、节点不知道"。
2. **确定性幂等键**保证即使有人绕过事务重放（例如手工调接口），`POST /api/jobs` 那条路径也只会返回原行。
3. **原子状态转换**（`WHERE status='ready'` ＋ `rowcount` 判定）保证连点两次重试、或两个进程同时推进，只有一个能赢。

反过来说，绝对不允许的做法是：先建 Job、再回写节点，中间没有事务。那是 `extraction_submit` 现在的形状，也是附件 §6.3 点名的三种坏状态的全部来源。

### 2.4 一条实测反证：恢复与"旧 worker 回来收尾"不会互相覆盖

产线一旦按 `job_id` 修节点状态，"Job 的终态会不会被回跳"就成了地基问题，所以这一条没有靠读代码推断，而是在临时库里真跑了一遍（假适配器、不碰 `data/`）：

```
领取到： True starting
recover_stale： {'failed': 1, 'cancelled': 0, 'needs_attention': 0}
恢复后状态： failed worker_lost
旧 worker 收尾后： failed | elapsed_ms = None | error_code = worker_lost
结论：终态被覆盖了吗 → 否
cancelled() 反证：failed → cancelled（worker_id 传的是别人） → 覆盖成立
```

前半段是好消息，而且**好在哪里要说清**：`recover_stale()` 收尾时把 `worker_id` 置 NULL，而 `succeed()`／`fail()`／`needs_attention()` 的 WHERE 都带 `AND worker_id = ?`，于是失联后被恢复的作业，原 worker 就算活着回来也写不动它。这不是巧合，是这三条 UPDATE 的归属守卫起了作用——**产线的恢复逻辑绝不能绕过它**（例如为了"修节点"去直接 UPDATE job 行）。

后半段是唯一的缺口：`cancelled()` 的 WHERE 只有 `id`，用一个完全不相干的 `worker_id` 也能把已恢复的行改成 `cancelled`。危害有限（状态同为终态，被覆盖的是收尾证据那三列），列进 §8 的 R1。

## 3. 推进节拍：审核完成后怎么让产线继续（三个技术问题之三）

**现有系统没有任何回调、事件总线、消息队列或后台定时任务**（除 worker 自己的轮询循环）。所有跨模块的"推进"都是**读时派生**：

- `audio_sync()` 在音频列表接口里逐行调（`routers/audio.py:48`）；
- `_extract_run_materialize()` 在抽取详情视图里调（`services.py:679-682`）；
- 看板、worker 告警、项目进度全是请求时现算。

这套模式的好处是**永远不会出现"通知丢了"**——状态是从事实现算的，不是从消息里攒的。坏处是**没人打开页面就没人推进**。

产线不能只靠读时派生（一集跑几十分钟，人不会一直盯着页面），所以需要一个常驻节拍。两条路：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（推荐）** | 调度器住在 **worker 进程**：`worker.main()` 的循环里，在 `recover_stale()` 之后加一句 `pipeline.tick()`——修节点状态、算可执行节点、提交下一条 Job | worker 已经是常驻循环、已经有恢复节拍、已经是唯一会写 Job 状态的进程；一个进程内只有一处推进，天然不会两个调度器打架。代价：worker 从此也写 pipeline 表（它今天写 `job`／`worker_state`／`model_validation`） |
| B | API 进程内起后台线程（`asyncio` task 或 `threading`） | uvicorn 的进程数与重启语义不在我们手里；多进程部署时会同时出现 N 个调度器，只能靠数据库锁互斥——为了省一行 worker 代码，换来一个必须靠锁才正确的系统 |

配套：`POST /api/pipeline/runs/{id}/advance` 仍然要有（人点一下"继续"、审核签完字前端顺手调一次），但它必须与 `tick()` **共用同一个幂等推进函数**，不能是两套逻辑。附件 §6.3 说的"审核回调重复执行"就是这么防的：审核中心不发通知，产线自己去看审核结论，看的过程是幂等的。

**审核结论怎么被产线看到**（依赖 §4 的 D1）：审核中心把结论写进它自己拥有的表，产线节点只存 `review_id` 引用，推进时现读。产线不写审核结论，也不复制它。

## 4. 必须先裁的三件事（阶段 B 开工前）

### D1　镜头级人工审核落在哪里（影响不变量 3）

现状：审核中心的两张表都以 `doc_id NOT NULL` 为轴，签字锚点是**正文里的字符偏移**。关键帧与镜头视频没有正文，也就没有锚点，今天**无处可签**。

`model_validation` 的 `artifact_review` 档看着像，但它判的是**模型槽位**能不能上生产（`production_ready` 的三条件之一），不是"这一镜的这一张图行不行"，不能挪用。

三个方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| **甲（推荐）** | 迁移里把 `review_item` 扩成多态审核对象：加 `target_kind`（`document/shot/job`）与 `target_id`，`doc_id` 改可空，唯一约束改成 `(target_kind, target_id, base_version, anchor)`；审核中心的接口与页面同步加"镜头审核"这一类 | 保住不变量 3 的字面意思（**一个写入口**＝审核中心这一个模块），签字、版本失配、驳回语义全部复用；代价是要改 `repositories/reviews.py`、`services.review_*` 与审核中心页面，属于"扩现有模块"，不是重构 |
| 乙 | 新建 `review_artifact` 表，仍由审核中心拥有（写入口仍在 `routers/review.py`） | 表更干净，但"签字"这件事出现两张表、两套查询、两个页面区块，正是这个项目一直在避免的第二事实来源 |
| 丙 | 产线自己记审核结论（`pipeline_node_run.output_json` 里存 approved） | **否决**：直接违反不变量 3 与附件的禁止事项 |

### D2　提交协议是否照 §2.3 落地（事务 ＋ 确定性幂等键 ＋ 原子转态）

推荐照做。附带一条：**顺手把 `extraction_submit` 的两步也包进 `transaction()`**（同样是纯库内写，符合边界），把那个已知的"孤儿付费 Job"窗口关掉。这是 2 行改动，但它改的是现有模块的行为，需要你点头。

### D3　调度器住在 worker 进程（方案 A）还是 API 后台线程（方案 B）

推荐 A。附带影响：`worker.py` 从此 import pipeline 模块；worker 挂掉时产线也停止推进（但 Job 恢复语义不变，重启后 `tick()` 会把节点修回来）。

## 7. 建议的最小数据库迁移方案（**本轮未创建**）

一个迁移：`migrations/0025_pipeline.sql`，四张表，`permission` 表不动（零新增权限点）。表数 26 → 30。

```
pipeline_template   id INTEGER PK, name, version, description, definition_json,
                    enabled, created_at, updated_at
                    UNIQUE(name, version)          -- 发布后不改历史版本，改就是新版本
pipeline_run        id INTEGER PK, project_id → project(id) ON DELETE CASCADE,
                    episode_id → episode(id) ON DELETE CASCADE,
                    template_id → pipeline_template(id), template_version,
                    paused INTEGER, cancelled INTEGER,      -- 只存这两个外生意愿位
                    cancel_reason, input_snapshot_json,
                    idempotency_key TEXT UNIQUE,            -- 防重复点"开始生产"
                    started_at, finished_at, created_at,
                    created_by → app_user(id) ON DELETE SET NULL
                    UNIQUE(project_id, episode_id, idempotency_key)
pipeline_node_run   id INTEGER PK, run_id → pipeline_run(id) ON DELETE CASCADE,
                    node_key, node_type, status,            -- 只存六个真实态，见 §5 第 8 条
                    depends_on_json, input_json, output_json,
                    job_id → job(id) ON DELETE SET NULL,    -- 只引用，不复制任何 Job 字段
                    review_id INTEGER,                      -- D1 定了才知道指向哪张表
                    retry_count, attempt_key,
                    error_code, error_message,
                    started_at, finished_at, created_at
                    UNIQUE(run_id, node_key)                -- 附件 §6.3 要的那一条
pipeline_event      id INTEGER PK, run_id → … CASCADE, node_id → … SET NULL,
                    event_type, payload_json, created_at    -- append-only，只 INSERT
                    INDEX(run_id, id)
```

四条设计约束（都来自现有代码已经付过学费的地方）：

1. **外键一律 `ON DELETE CASCADE` 到 `project`**：删项目时产线记录跟着走，与 `job`／`document`／`audio_clip` 同一口径；`job_id` 用 `SET NULL`，因为删一条 Job 不该把节点历史抹掉（节点还要能说"我关联的作业已经没了"）。
2. **`episode_id` 用 CASCADE 而不是现有 `job.episode_id` 的 SET NULL**：一集删了，这集的产线运行就没有意义了；留着会产出一堆指向空的运行记录。（这一条与 `job` 不同，需要你确认。）
3. **迁移期间 `PRAGMA foreign_keys=OFF`**（`migrate.py` 已经这么做），所以 `pipeline_event.node_id` 的 `SET NULL` 在删表重建场景下不会自动触发——本轮不涉及重建，写在这里是给下一轮的人提个醒。
4. **一个迁移一个事务**，`migrate.py` 会在应用前自动整库备份（保留 5 份），新库初始化与老库升级走同一条路径。

`node_type` 的稳定枚举（附件 §5.2 的 13 种）建议写进 CHECK，而不是让前端传字符串：`project_input/episode_input/document_input/shot_validate/asset_validate/human_gate/image_generate/image_review/video_generate/artifact_validate/shot_review/audio_prepare/export_prepare`。

### 14.2 验收撞出的三条真缺陷（已修＋回归）

1. **失败运行永不收尾**。`_finalize` 原来只认"所有节点都在终态"，而前置失败／取消之后，下游 `pending` 节点会一直是 `blocked`，永远到不了终态——`finished_at` 落不下来，同一集此后每次发起都 409。修法：新增 `_unreachable(nodes)`，把可传递地不可达的 pending 节点排除在"还在跑"之外。回归：`test_失败收尾之后同一集能再起一条`。
2. **重试不重开已结束的运行**。重试只把节点改回 `running`／`pending`，但 `finished_at` 还留着，运行仍显示已结束。修法：重试事务里调 `repositories/pipeline.reopen()` 清空 `finished_at`。回归并入 `test_一镜失败只重试那一镜`（断言重试后 `finished_at == ""`）。
3. **取消留下可签的人工节点**。取消时 `human_gate`／审核节点没有作业可取消，原来原样停在 `waiting_review`；迟到的签字能把它收成 `completed`，让一条已取消的运行动起来。修法：`cancel_run` 对"等签字且无作业"的节点直接收成 `cancelled`。回归：`test_取消会收掉还在等人签字的节点`。

- **多 worker**：0029 新建 `worker_node`（每进程一行心跳与 `limits_json`），`worker_state` 保留镜像；CLI 可声明 `--max-global` 与五类上限，默认仍是全局 1、每类 1。
- **整季**：0030 新建 `season_run`／`season_item`；每集仍是一条独立 `pipeline_run`，批次只存 `paused／cancelled／finished_at` 与冻结的 `max_active_runs`；`seasons.tick()` 在 worker 每轮 `pipeline.tick()` 之前按上限补集。
- **失败恢复**：只重试失败节点，跳过被驳回的审核节点；已成功镜头、旧产物与旧签字不动。
- **证据边界**：双 worker 是真进程、真队列、真 SQLite 事务；整季的生成节点仍走 mock 适配器，不是真实模型生产验证证据。
