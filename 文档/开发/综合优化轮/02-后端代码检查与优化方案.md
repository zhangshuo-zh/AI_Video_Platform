### P0-1b 引擎端点 SSRF + 云视频下载无边界 ✅ 已确认（CWE-918 / CWE-400）

> 由安全专项审查补回，已逐条实测复核。**这是本次唯一「确认可利用且后果不止于信息泄露」的安全项**；触发需 `system:config` 权限或被诱导的管理员 / 被劫持的供应商应答，因此定为 P0 而非「外部直接 RCE」。

- **证据（三条链路）**：
  1. [repositories/engine_instances.py:70-99](../../app/backend/repositories/engine_instances.py#L70-L99) `validate_endpoint` 只校验 `http://`、无凭据/query/fragment/路径、端口 1024–65535，**未禁止 loopback / 私网 / 链路本地（`169.254.0.0/16`）/ 保留地址**。
  2. [engines.py:118-146](../../app/backend/engines.py#L118-L146) `_get_info_for()` 直接 `urlopen(endpoint + path)`，失败时回显 `f"{url} 连不上：{reason}"` / `f"{url} 返回 HTTP {exc.code}"`；[routers/model_center.py:645-660](../../app/backend/routers/model_center.py#L645-L660) 的 `POST /api/engines/{id}/probe` 把 `status.detail` 与 `endpoint` 原样回给调用方 → **内网存活/端口探测，若内网服务返回带 `model` 的 JSON 还会进 `engine_model` 回显**。`engine_http_run.py:68-83`、`llm_http_run.py:108-125` 同样把端点拼进 `urlopen`。
  3. [cloud_run.py:93-105](../../app/backend/cloud_run.py#L93-L105) `_download()` 对 `video_url` 直接 `urlopen` 后 `while True: chunk=resp.read(256KB); fh.write(chunk)`，**无累计大小上限、无 Content-Type 校验、无主机校验**；`video_url` 来自供应商应答（[cloud_run.py:275-279](../../app/backend/cloud_run.py#L275-L279)）。恶意/被劫持的 `ALIYUN_WAN_BASE_URL`（管理员可配环境变量）可让它指向 `http://169.254.169.254/...` 或一个无限流，把 GB 级数据写进 `JOBS_DIR`。
- **攻击场景**：管理员新建 `endpoint=http://169.254.169.254:80` 的引擎实例并点「探测」，服务端向云元数据/内网地址发 GET 且把结果回显；或供应商应答里的 `video_url` 指向内网/无限流，worker 落盘撑爆磁盘。
- **修复（上线前必修）**：
  - 在 `validate_endpoint()` 里 `socket.getaddrinfo(host, port)` 逐条解析，用 `ipaddress` 拒绝 `is_loopback`/`is_private`/`is_link_local`/`is_reserved`；**对 DNS 重绑定要防**（解析结果逐条校验，且实际连接使用已校验的 IP，或加 `FASTVIDEO_ENGINE_ALLOW_HOSTS` 显式白名单）。本机引擎（如 `127.0.0.1:7860`）若业务需要，走白名单显式放行，不要全放开。
  - 抽一个 `_safe_url(url)` 统一给 `cloud_run._download` / `_get_json` / `_post_json`、`engines`、`engine_http_run`、`llm_http_run` 用；**禁止自动跟随重定向**（urllib 默认跟 302，需自定义 `HTTPRedirectHandler` 对每一跳复发校验）或直接禁跟随。
  - `_download` 加 `max_bytes`（如 2GB）累积判断 + `Content-Type` 白名单（video/mp4 等）+ mp4 `ftyp` 头校验，超限即抛。
  - 测试：`127.0.0.1:7860`、`169.254.169.254:80`、`10.0.0.5:8080`、`[::1]:7860` 全部抛错；monkeypatch `getaddrinfo` 返回私网验证被拒；集成测 `POST /api/engines` + `/probe` 断言 422 且未发起请求。

### P0-1c `retry_node` 在事务外建新 Job，可留下「无归属的付费作业」 ✅ 已确认

> 由数据层专项审查补回，已复核。**改动量最小、收益最明确的一条**：把一行代码移进事务即可。

- **证据**：[pipeline.py:1618-1625](../../app/backend/pipeline.py#L1618) ——
  ```python
  new_job_id = job_repo.retry(job, user_id)["id"]     # ← 先提交（自己的 get_conn）
  new_status = NODE_RUNNING
  with transaction():                                 # ← 事务从这里才开始
      pipeline_repo.reset_for_retry(node_id, job_id=new_job_id, ...)
      pipeline_repo.reopen(run["id"])
      pipeline_repo.add_event(...)
  ```
  [repositories/jobs.py:626-674](../../app/backend/repositories/jobs.py#L626) 的 `retry()` 自己开 `get_conn` 并提交，含一条 `INSERT job`（新作业，状态 `queued`）+ 一条 `UPDATE`（旧作业 `superseded_by_job_id`）。
- **影响**：进程若在两行之间崩溃，新 Job 已 `queued`、worker 会领走并可能产生云端调用/计费，但产线节点仍指向旧 Job，界面查不到这条新作业——正是项目自己 D2 裁定要避免的「花钱但无归属」。`pipeline.start_run`/`advance_run`/`agents.create_run` 等其它跨表写都正确包在 `transaction()` 里，**这是唯一漏网的一处**。
- **建议**：把 `job_repo.retry()` 一并移进 `with transaction():` 内（`retry` 与 `reset_for_retry` 都走 `get_conn`，会自动借用同一条连接），`new_job_id` 在事务内算好再传给 `reset_for_retry`。全程纯库内写，不碰文件/网络，正好落在 [db.py:61-63](../../app/backend/db.py#L61) 允许的边界内。同为「事务外跨表写」的还有 [routers/content.py:525](../../app/backend/routers/content.py#L525) 的 `assets.add_image` 上传路径（与 `:748` 的导入路径不对称，两人同时传同一资产会互相覆盖 `ref_images` JSON），建议一并补 `with transaction():`。

### P0-1d Python 层 `backend` 枚举与 DDL 漂移，`remote` 验证被堵死 ✅ 已确认

### C.2 一个值得记下的教训（测试写法）

第一版 `test_git错误回给前端的文案不含部署机绝对路径` 只测了 `_git_detail()` 辅助函数本身。我把路由改回 `detail=f"...{err}"` 做回归验证时——**测试照样绿**。也就是说它根本没在守"调用点用了脱敏"这件事。

改成走真实 HTTP（`as_role` + `fresh_project` + 桩 `commit_file`）后，同样的回退操作立刻失败：

```
AssertionError: 部署机路径不该跟着错误出门：
正文没能提交到 Git：fatal: Unable to create '/var/folders/…/workspace/.git/index.lock': File exists.
```

凡是"某个辅助函数必须被某个调用点使用"的约定，只测辅助函数等于没测。这一条对 B.3 里同类断言同样适用。

### E.1 修掉一个真实可见的缺陷：`[object Object]`

改之前，错误响应有**两套形状**：

| 来源 | 形状 | 前端表现 |
|---|---|---|
| 业务拒绝（手写 `HTTPException`） | `{"detail": "作业不存在"}` | 正常显示这句话 |
| 校验拒绝（Pydantic/FastAPI 默认） | `{"detail": [{"type":..., "loc":..., "msg":...}]}` | **`[object Object]`** |

前端 `api.js` 的写法是：

```js
let detail = JSON.parse(text).detail ?? text;
const err = new Error(detail);
```

数组进 `new Error()` 会走 `Array.prototype.toString()`，元素是对象 → `[object Object]`。
也就是说：**用户漏填一个必填项时，弹窗里只有这五个字**，没有任何可用信息。

实测修复前后：

```
修复前  422 {'detail': [{'type':'missing','loc':['body','name'],'msg':'Field required'}]}
修复后  422 {'detail': 'name：缺少必填项', 'code': 'invalid_payload'}
```

`loc` 开头的 `body`/`query`/`path` 对人是噪音，剥掉；多条用 `；` 分隔；
不认识的 Pydantic `type` 退回原文 `msg`（英文，但至少不是 `[object Object]`）。

### E.2 新增 `errors.py` 作为 HTTP 错误码的唯一出处

- `BY_STATUS`：状态码 → 默认错误码（`401→unauthenticated`、`404→not_found`、
  `429→rate_limited`…）。**业务代码不写 code 也自动有**——所以这一个端点都不用改。
- `detial_text()`：把任意 `detail`（str / list / dict / Exception）压成**一句人话**。
  这条函数就是"detail 恒为字符串"那道闸。
- `VALIDATION_HINTS`：常见 Pydantic type 的中文说法（`missing→缺少必填项` 等）。

**与 `error_catalog` 不合并**——这是刻意的，理由写进了模块头注释：

- `error_catalog` 答「一条**作业/节点**失败后，人该怎么理解与处理」，
  七字段诊断，写进 `job.error_code` 与节点输出，面向**已经发生的一次执行**；
- `errors.py` 答「一次 **HTTP 请求**为什么被拒」，面向**这一次调用**，不改任何作业状态。

两者取值域目前并不重合（HTTP 是 `not_found`/`forbidden`/`conflict`；
执行失败是 `adapter_*`/`provider_*`/`run_timeout`）。强行合并会把两个不同
生命周期的东西塞进同一张表，改一个动另一个。共用的是命名风格，不是表。

### E.3 两个 handler，三条纪律

`main.py` 加了 `RequestValidationError` 与 `HTTPException` 两个处理器，纪律：

1. **`detail` 永远是字符串**（前端既有写法不用改一行）
2. **`code` 是稳定的**，前端 switch 可以依赖；`detail` 是可以改文案的
3. **只加字段、不改既有内容**——浏览器验收与说明书引用过那些句子，
   实测 `GET /api/jobs/999999` 的 detail 仍是原文「作业不存在」，一字未改

### E.4 补 `response_model`：只加在验证过的地方

先看覆盖率（端点 / 带 `response_model` 的比例），最差的四个：

```
agents.py 0/11   production.py 0/7   dashboard.py 0/3   workbench.py 0/1
```

**但这四个我都没加。** 原因不是偷懒，是它们返回的是动态组装的聚合视图
（`services.workbench()`、`services.project_dashboard()` 直接返回 dict，
键随分支变化——`/context` 有时带 `cleared` 有时不带），而且 `models.py` 里
**没有** `WorkbenchOut` / `AgentRunOut` / `ProductionOut` 这类现成模型可复用。

这里有个关键机制必须先说清：**`response_model` 会静默剔除未声明的字段**。
实测：

```python
@app.get("/y", response_model=Out)   # Out 只有 a/b/c
def y(): return {"a": 1, "zzz": 9}
→ 200 {'a': 1, 'b': None, 'c': ''}   # zzz 被无声吃掉，没有警告
```

也就是说，给这类端点**硬加一个模型比不加更危险**：漏写一个字段，
前端就收不到它，而接口 200、测试可能仍然绿。`overview.js` 依赖
`c.review_documents` / `c.runs_active` 这些键，丢一个就是空指针式的显示错。

所以这一批只补了两处**真正形状固定**的：

| 端点 | 为什么安全 | 验证方式 |
|---|---|---|
| `GET /api/health` | 两个字段，无分支 | 新增 `HealthOut` |
| `GET /api/jobs/{id}/diagnosis` | `error_catalog` 的 55 条 + `UNKNOWN_TEMPLATE` **键组合完全一致**（已用脚本核对：只有 1 种组合） | 新增 `JobDiagnosisOut`/`JobDiagnosisBody`；**逐字段比对原始响应与过滤后响应，确认零丢失** |

剩下 71 个无 `response_model` 的端点，正确做法是**先把聚合视图收成模型**
（那属于结构重构，要连带改 services 层），而不是在路由上贴一个漏字段的壳。
这一条写在这里，是为了避免下一轮有人为了刷覆盖率数字去贴模型。

### F.1 方法：先测绘，再建模，最后才挂 `response_model`

`response_model` 会**静默剔除**未声明的字段（附录 E.4 实测过）。所以这一批的顺序是：

1. **测绘**：把服务层的真实返回 dump 出来，递归列出每条键路径与类型
2. **建模**：照测绘结果写模型
3. **比对**：把模型序列化的结果与原始返回**逐键比对**，必须完全一致
4. **挂载**：比对通过才在路由上加 `response_model`

第 3 步是关键。这一批用它抓到了**三处凭名字猜错的类型**：

| 字段 | 我以为 | 实际 |

| `stats.memory.parallel_reference` | `str` | `dict`（"每类能力最多并行几条"的分档依据） |

| `stats.signs` | `dict[str, int]` | `dict[str, dict[str, int]]`（外层是签字对象种类，内层是 decision→数） |

三处都是被 Pydantic 当场拒掉的（`Input should be a valid string, input_value={}` 之类），
