## 1. 现有系统架构图

```
浏览器（原生 ES module，无框架、无 node）
  index.html → js/app.js（路由 #module/sub/param）
    ├─ js/modules.js        12 个一级模块的唯一定义（含权限点、二级页）
    ├─ js/store.js          唯一前端状态源：projects / currentId / user / permissions / worker
    ├─ js/navstate.js       二级页下标 + 详情深链 + 跨模块一次性草稿（jobPrefill）
    ├─ js/api.js            所有 /api 调用（fetch）
    ├─ js/validation.js     健康／验证／作业状态／告警码的唯一译名出处
    ├─ js/enums.js          能力／模式／登记来源／计费单位
    └─ js/views/*.js        18 个视图（projects / writing / assets / asset-studio /
                            asset-triage / asset-detail / generate / review / audio /
                            pipeline / composition / models / overview / knowledge …）

            │ HTTP JSON（同源，静态页与 /api 由同一个 uvicorn 进程托管）
            ▼
FastAPI（app/backend/main.py，按 router 挂载）
  routers/  auth users projects content documents extraction profiles
            jobs audio review seasons pipeline compositions
            dashboard workbench model_center settings files
  ── 业务层 ──
  services.py        提交作业、解析默认轨（resolve_provider，唯一选路出口）、
                     文档 AI、抽取物化、音频台账、看板、worker_status
  pipeline.py        模板／节点／依赖推进／生产前检查 preflight()
  seasons.py         整季批量（一次推进 N 集，上限防呆）
  asset_studio.py    资产创作（文字设定、图像候选、命名形态）
  extraction.py      正文 → 候选（人物／场景／道具）
  reviewgate.py      校验器 gate 与签字锚点
  composition/       timeline.build（取片与签字判定）· service（建版本、发起合成）
                     ffmpeg_runner · subtitles · validators（ffprobe／字幕滤镜）
  model_center.py    清单 × 登记联表、四数、场景候选
  adapters.py        规格清单（参数／计价／出处／健康要求）——规格住代码，不入库
  runners.py         argv 构造：fastmetal / mlx-video / mflux / cloud
  runtime.py         本地运行时探测（解释器／入口脚本／权重）
  validations.py     五类验证出处、生产可用判定、徽章
  ── 数据层 ──
  repositories/*     SQL 唯一出口（ordering.py 管枚举顺序）
  db.py              SQLite WAL，transaction() 内共用连接，写锁 timeout=5s
            │
            ▼
  worker.py（独立进程） 领一条 → 起子进程 → 写日志/产物 → 续租 → 落状态
  data/jobs/<id>/outputs|logs   产物与日志；jobfiles.py 管路径边界
  workspace/ + gitrepo.py       稿件正文与版本历史（Git）
  FFmpeg / ffprobe              合成与技术校验
```

三条不能动的骨架：

1. **一条队列**。`job` 是唯一任务记录，`worker.py` 是唯一执行进程；`services.submit_job()` 是主提交入口（另有三处直连 `job_repo.create`：文档 AI、抽取、合成，数量由守卫测试钉住）。
2. **一份选路**。`services.resolve_provider()` 只看 `provider_config.is_default`，不补位、不兜底；云端视频必须逐镜头显式选择并确认计费。
3. **一份成本**。云端费用只记在 `job` 上（`cost_micros`／`billable_status`），别的模块只读不另算。

## 2. 模块与核心业务对象关系图

```
project ─┬─ episode ── shot ───── job ─────(产物: data/jobs/<id>/outputs)
         │                │           │
         │                │           ├─ review_item(target_kind=job)  人工签字
         │                │           └─ resources_json / cost         机时与费用
         │                ├─ asset_ids ──→ asset ─┬─ asset_variant（形态，含 ref_images）
         │                └─ variant_ids ─┘       └─ asset_character_profile
         ├─ document（小说／剧本，正文在 workspace/，版本在 Git）
         │     └─ extraction_run ── extraction_item（候选池）──→ 接受/合并/驳回
         ├─ audio_clip（台词／旁白／音乐／音效）── job_id ──→ job
         ├─ composition（版本化时间线快照）── job_id(ffmpeg) ──→ 成片文件
         ├─ pipeline_run ── pipeline_node_run ──→ job / review / composition
         └─ season_run ── season_item ──→ pipeline_run

provider_config（10 槽：5 能力 × 本地/云端，默认轨唯一来源）
model_registration（这台机器上的实例登记）
model_validation（五类验证出处，只追加）
model_policy（9 个任务场景的建议轨/备用轨——**目前没有任何业务消费方**）
generation_profile（参数模板）
app_user / role / permission（18 个权限点）/ session / doc_lock
worker_node / worker_state（心跳与并发实况）
```

要点：资产**不属于集**，它属于项目（`asset.project_id`），可跨集跨镜头复用；镜头通过 `asset_ids` 与 `variant_ids` 引用资产与形态，引用关系已经在 `shot` 行里，不需要也不允许再往 `shot` 表塞人物／场景／道具的冗余字段（任务书 §13 的要求与现状一致）。

## 3. 现有生产流程图

```
项目中心 建项目 → 创作中心 建集 → 文档（小说/剧本）→ 保存（Git 版本）
        → 「抽取」提交文本作业 → 候选池（extraction_item）
        → 资产中心·文本提取 逐条接受/合并/驳回 → 资产入库
        → 资产中心·资产创作 生成设定文字 + 图像候选 → 显式「存入」基础图/形态图
        → 创作中心·分镜 建镜头（summary/prompt/duration/asset_ids/variant_ids）
        → 分镜行「生成」→ 生成中心提交（本地/云端，云端要确认计费）
        → worker 执行 → 成功产物 → 审核中心·产物审核 签字（锚点=文件 sha256）
        → 两条出口：
           A 手动：成片中心「新建成片」→ timeline.build(require_approved=True)
                   → ffmpeg 合成 → 验收（时长/分辨率）→ 成片审核签字 → 导出
           B 产线：产线中心 选模板 v1/v2 → preflight → 建运行
                   → 节点按依赖推进（keyframe→image_review→video→shot_review
                      →audio_prepare→compose→export_validate→export_review，
                      v2 才含后三格；v1 止于镜头）
                   → 人工闸门节点等待审核 → 通过后继续 → 失败可单节点重试
```

## 7. 需要调整的数据库结构

迁移 `0037_production_context.sql`：

1. `user_context(user_id PK, project_id, episode_id, updated_at)`——服务端存一份当前上下文，换设备/刷新不丢。
2. `shot` 加五个可空文本列：`shot_size`、`camera_move`、`aspect`、`style`、`negative_prompt`（默认 `''`）。**不进 `shot_source_version()` 的指纹**：任务书 §6.3 列的触发面是内容／提示词／引用／形态／关键帧，把纯描述性字段塞进指纹会让"补填景别"变成"全片过期"。
3. 索引：`idx_shot_episode`、`idx_job_shot_status` 视现状补（先 `PRAGMA index_list` 查过再决定，不重复建）。
4. 不新增产物表、不新增第二套状态列：正式关键帧／正式视频继续由"签字成功的那条 job"表达（`review_item(target_kind='job')`＋`job.status='succeeded'`），避免与 `timeline.build` 的取片规则打架。

## 8. 可能存在的兼容性问题

1. **`pipeline.preflight()` 的返回形状**已被前端发起弹窗与 6 条测试依赖；重构必须保持 `blocking/warnings/info` 三键不变，否则界面与测试同时红。
2. **`shot_source_version()` 的字段面**一旦扩大，历史作业全部会被判"源已变"，签字集体失效——这是最贵的兼容性坑，所以新列一律不进指纹。
3. **`store.currentId` 与 `last_opened_at`** 已经在用；新增服务端上下文要与之同源，不能出现"顶栏一个集、页面另一个集"。
4. **切换集时的未保存内容**：文档编辑器有 `doc_lock` 与 `⌘S` 保存，工作台跳转必须走"先保存/放弃/取消"，否则任务书 §4.1 最后一条会翻车。
5. **产线与手动的成片版本**：`composition.version` 是按集递增、`pipeline_run_id` 可为空；新增预检不能改变"产线钉住 shot_jobs"的语义。
6. **音频**：`runners.build()` 至今没有 tts／music 分支，`services.audio_submit()` 在健康不是 ok 时直接拒（VoxCPM2／ACE-Step 连探测规则都没有）。工作台的"音频制作"阶段只能显示"尚未接入"，不许给一个会 500 的提交按钮。
7. **调用策略**：`model_policy` 没有消费方；工作台与预检都不许把它当路由依据。
8. **真实模型**：本机只有 FastMetal 1.3B 与 mflux Q4 两条真跑通的路；mlx-video／VoxCPM2／ACE-Step 无权重。业务验收场景必须在这两条路上跑，不能假装 14B 可用。

## 10. P2 的实施边界（先划清「能算的」与「不能算的」，再动手）

任务书 §15 的 P2 四项是 智能推荐、参数推荐、批量制作、生产统计。目标写得很清楚：**不是再加菜单**。所以这一节的判据只有一条——**这件事能不能从库里已有的事实算出来**；算不出来的，界面就不摆一个看起来像结论的东西。

**能算的（不新造判据，只派生已有事实）**

| 项 | 算什么 | 事实来自 | 放哪儿 |
|---|---|---|---|
| 生产统计 | 每项目×集的：镜头数、作业数、成功／失败／待核对条数、总耗时、总成本、签字通过率、驳回原因分布（按 `error_code` 与 `review_item.decision` 分组） | `job`、`review_item`、`cost` 列——**一处都不新写** | 项目工作台页内一块面板（不新增一级菜单、不新增页面） |
| 批量重做失败镜头 | 把这一集里所有「最新一条作业失败」的镜头一次重投：逐条落地、逐条报原因、上限一条口径、归属 403／404 原样抛出 | 与批量审核（P1 第 5 项）**同一条纪律**；提交仍走 `services.submit_job` | 项目工作台的下一步任务清单里选中若干行 |
| 参数推荐里「要跑多久」 | 这一集还要多少墙钟时间、内存峰值多少、能不能再并行一条 | 本轮实测：单镜 avg 32.8s、峰值 1.99GB（16GB 机器），1024 图像档另采 | 面板上一行，写明「依据＝本机实测哪几条作业」 |

**不能算的（要人给标准，没给就不做）**

- 「智能推荐」若指*哪个镜头该重做、哪一版画面更好*：需要质量标准或人工评分样本，平台现在两者都没有。`review_check` 里只有**人勾过的结论**，拿它训练"推荐"就是把人的两次点击当成规律。这一档不做，也不摆按钮——与音频执行未接线时不给提交入口是同一条纪律。
- 「推荐用哪一档模型」：`resolve_provider()` 是**不补位**的，配置说什么就是什么；界面替人换档等于绕开策略那条硬约束（裁定 MC1 已定：备用轨只提示不自动切）。

**四项的终局（2026-11-05）**：生产统计＝已完成并经过真实测试；批量制作＝已完成（`POST /api/jobs/retry-batch`，只重投本机失败与已取消，云端与待核对逐条拒）；参数推荐＝做了能算的那半（单条耗时、按秒采到的内存峰值、`(总量×0.8)÷单条峰值` 的并行参考，算式随数字一起显示），模型档位推荐**不做**（配置不补位，裁定 MC1）；智能推荐＝P0 的「下一步任务」就是它的规则形态，而「该重做哪一镜」**不做**（缺质量标准）。**做法与进度**：**生产统计面板**已于 2026-11-05 落地（`§4.18`，14 项新用例＋真浏览器 6 项，实测记录《03-业务验收记录》§14）；**批量重做失败镜头**未做。理由：前者回答的是排产最贵的那个问题（这一集还差多少时间多少钱、驳回都集中在哪一类码），且完全是读；后者把人现在要点 N 次的动作收成一次，复用 P1 已经验收过的批量纪律。两项都不新增菜单，符合目标的原话。
