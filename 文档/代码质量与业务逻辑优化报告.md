## 4. 逐项成因与修复

**问题 1（重试洗素材）**：`jobs.retry()` 的 INSERT 列表是从原作业抄字段时漏了 `source_version`，新行落库即为空串，而 `job_source_stale()` 的第一条规则正是"空串不判过期"（这条规则本身是对的，为的是不把 0031 之前的历史作业全打成废纸）。于是重试一次就顺带把"素材已过期"擦掉，人拿到新产物、界面上没有任何一处说它来自旧内容。修复是把 `source_version` 加进复制列表，与提示词快照同等对待——**重试的语义是"同样这份源内容再来一次"**，改没改源内容该由人再点一次生成，不该由重试顺手认定。

**问题 2（两把尺子）**：分镜列表与成片各自写了一句形状相似但语义不同的 SQL。收成 `jobs.latest_succeeded_videos_by_shot(episode_id)` 一个出处（`capability='video'` ＋ `status='succeeded'` ＋ 每镜 `MAX(id)` 的窗口子查询）。同时删掉 `compositions.latest_video_jobs`（问题 6）——那条 SQL 放在成片仓储里，本身就是"Job 的读法可以各写一份"的邀请。

**问题 3（可重试性）**：判定散在 `pipeline.retry_node` 的四个 raise 里，前端只能按 `status === 'failed'` 猜。抽出 `retry_gate(node, run, job=None)` 返回同一个结论，供"要不要摆钮"与"点下去拦不拦"两处共用——**同一个判断不留两份**，否则接口改了页面还在骗人。字段缺失时（老服务端配新页面）前端退回旧判法，不报错。

**问题 5（原因分批）**：`build()` 里镜头问题收集完就 raise，音频那段代码在其后。改成两支都收集完再一次性抛 `CompositionInvalid(reasons)`。这里有一个反向约束本轮**刻意没动**：`_shot_review()` 只按 `base_version` 筛签字，不按锚点筛——按锚点筛会把历史上只签过 `artifact:0` 的签字判成没签，属行为回归。

**问题 4／7／11／12（前端）**：见 §7.3。

## 7. 数据库、任务与前端优化

### 7.1 数据库

迁移 `0032` 只加一条索引：`idx_job_episode_status ON job(episode_id, status, shot_id)`。取证（同一份合成数据，`EXPLAIN QUERY PLAN`）：

```
加索引前：SEARCH job USING INDEX idx_job_queue (status=?)；USE TEMP B-TREE FOR GROUP BY
加索引后：SEARCH job USING COVERING INDEX idx_job_episode_status
          (episode_id=? AND status=? AND shot_id>?)
```

现役库（本机 `data/platform.db`，迁移前快照 `platform.db.bak-20261103-222419`）应用后 `integrity_check` 为 ok，计划与临时库一致。**没有顺手加第二条**：`WHERE project_id = ?` 那几条已经走 `idx_job_project`，只是排序要临时 B 树——每项目几十行的量级换不到什么，却要多维护一份 B 树。这个理由写在迁移注释里，不留在聊天记录里。

### 7.2 读路径（`tools/bench_queries.py` 现测）

合成 24 集／312 镜／936 条成功视频作业，改动前后两棵树各跑一次。**结论看次数与行数，毫秒只作参考**：

| 读路径 | 回库次数 | 读行数 | 中位毫秒（参考） |
|---|---|---|---|
| 分镜列表 `shots_view` | 123 → **9** | 106 → 32 | 17.85 → 1.30 |
| 产线运行详情 `run_view` | 54 → **18** | 47 → 35 | 7.12 → 2.44 |
| 成片列表 `list_for_project` | 15 → **6** | 11 → 6 | 1.94 → 0.82 |
| 产线运行列表 `runs_for_project` | 12 → **9** | 8 → 6 | 1.56 → 1.11 |
| 生产前检查 `preflight` | 34 → **28** | 31 → 29 | 4.15 → 3.15 |
| 首页工作台 `workbench` | 153 → **153（未动）** | 75 → 75 | 20.82 → 20.74 |

脚本本身留在仓库里：用 `sqlite3.connect(..., factory=CountingConnection)` 覆盖 `execute` 数回库，包装 `subprocess.run` 数探针次数（子进程本轮全部为 0，说明没有把读路径改成多进程）。

### 7.3 任务与队列

**一条都没改语义**：领取仍是 `BEGIN IMMEDIATE` ＋ 全局／每类原子上限，租约、`recover_stale`、`needs_attention` 不自动重试、账单核对、幂等键全部照旧。本轮只动了两处外围：`retry()` 补字段（问题 1）与 worker 资源占用的磁盘读数改用 `volume_usage()`。这是刻意的——任务与队列是这套平台唯一同时管着钱和事实的地方，动它必须有独立授权与独立验证轮。

### 7.4 前端

- **过期响应**：`router.renderView` 每次进入取自增序号，`await` 回来发现不是最新就整个丢掉；五个视图各带自己的请求号或"我要的那一个还在不在"的判断（成员弹窗、抽取预览、校验报告、生产前检查、镜头候选）。
- **监听归属**：`#view-root` 是常驻节点，路由只换它的 `innerHTML`；把 `click`／`keydown` 绑在它上面等于每进一次页面叠一对监听，旧闭包抓着已离开文档的菜单却仍 `hidden === false`，切页后还在抢 Esc。项目中心两处改绑视图自己渲染出的 `<section>`。
- **不演空态**：读失败写页面提示条，并与提交失败共用同一条提示的收走时机。

## 8. 业务规则与版本一致性变化

| 规则 | 本轮前 | 本轮后 |
|---|---|---|
| 「源已变」判的是哪条作业 | 这一镜最新一条成功作业（不分能力） | 这一镜最新一条**成功的视频作业**，与成片前置检查同一个出处 |
| 重试后的源版本 | 新作业留空＝不判过期 | 新作业**继承**原作业的版本，过期结论不因重试而消失 |
| 成片发起失败时报原因 | 镜头一支报完才可能报音频 | 两类原因同一个异常一次报完 |
| 节点能否重试 | 前端按状态猜 | 服务端一处判完并下发结论与一句人话原因 |
| 签字入口 / 状态真相源 / 成本口径 / 资源类映射 | 审核中心唯一、Job 现算、只在 Job、`RESOURCE_CLASS_SQL` 唯一 | **未变** |

版本号与状态一致性上本轮确认了两件事没有第二份真相：`shot.revision` 与 `job.source_version` 仍是"读时现场比"，没有新增状态位；成片 `composition` 仍不存状态，时间线冻结。为"性能"引入第二份状态的路都被否掉了（例如把 `source_stale` 落列）。

## 9. 迁移与向后兼容

- **只有 0032 一个新文件**，内容是一条 `CREATE INDEX IF NOT EXISTS`：不改列、不改约束、不搬数据，历史迁移一字未动。
- **`retryable`／`retry_hint`** 在 Pydantic 模型里带默认值，老前端拿到新响应无感；新前端拿到老响应时按"缺字段＝退回旧判法"处理，不会整页报错。
- **旧作业（0031 之前、`source_version` 为空）仍不判过期**，本轮未收紧——收紧会把历史产物全打成废纸，也会让已经签过字的片子凭空失效。
- **重试继承 `source_version` 对历史数据的影响**：只影响此后新建的重试行，已经落库的旧重试链不回填（回填＝替历史作业编造当时没有的指纹）。
- **部署侧**：现役库已应用；无待执行的清理脚本；`FASTVIDEO_DISK_MIN_FREE_GB` 有默认值，不设也能跑。
